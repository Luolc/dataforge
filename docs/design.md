# dataforge design

The current design, edited in place. Why a decision was made lives in the PR that made it. Only an orchestra-triggered design pass edits this file; other PRs describe their effect on it under "Design impact".

## 1. What this is, and what it is not

dataforge is the shared part of a "data machine": a small multi-agent workshop that builds datasets with coding agents (today Claude Code, the only agent the runtime supports). Each dataset lives in its own repo. This repo holds what every dataset repo shares:

- the machine setup that turns a fresh Ubuntu 24.04 machine into a data machine;
- the files every agent on the machine gets (the base `AGENTS.md`; section 6);
- a Python package, `dataforge` in `python/`, that dataset repos install; its module `dataforge.curation` holds the state machine that runs an attempt at one data item, the states and actions it ships, and a Harbor trial runner (section 5); its module `dataforge.runtime` runs coding agents headless, Claude Code through `dataforge.runtime.claude` (section 5, "The Claude Code runner"), and reads the traces of Pi and Codex CLI through `dataforge.runtime.pi` and `dataforge.runtime.codex` (section 5); its optional module `dataforge.gateway`, a model gateway (section 5, "The gateway"); its module `dataforge.queue`, a queue of jobs on one machine (section 5, "Scheduling"); its modules `dataforge.task` and `dataforge.testrunner`, planned, the generic `[metadata]` of a Harbor task's `task.toml` and the native test runners copied into each task, which write their results as CTRF (section 5, "Harbor tasks"); and its optional module `dataforge.viz`, with a frontend in `web/`, a web viewer of attempts and of the job queue that writes only to the queue, whose design is [`design-viz.md`](design-viz.md).

Starting agents, carrying messages between them, tracking who owes work and flagging stuck agents belong to Agent Fleet, a separate project. The setup installs its `fleet` binary and the tools it calls (fednet, atb, statute), each at its latest release (invariant 2); configuring and running them is the machine's own provisioning (section 4).

How a dataset repo works, which dataforge supports but does not enforce: whoever writes a change does not merge it, and a separate agent reviews before merge; a change to the dataset-level acceptance criteria passes a two-arm regression, the reference sample scoring full marks and an empty output failing, while per-item check scripts ship with the data and go through normal review; specs (what to build, what counts as acceptable) are edited only by people; runtime state lives on the machine under `~/scratch/<repo>/` and is never committed: `progress/<job>.log`, an optional `board.md`, and `lessons.md`, where any agent writes suggestions that become PRs.

Not in scope: dataset-specific code and dependencies, which stay in the dataset's repo, including the states of the state machine and what each does (its prompts, validators, checks, rubrics, how pass@k is judged, its caps and the text of each report) and, of a Harbor task, the kinds a test may have, the rules of each suite, how a test is judged, the dataset's own `[metadata]` groups and which keys its exports keep; how a test is run, its result format (CTRF), the test manifest's format, the generic `[metadata]` schema and the allow-list mechanism are dataforge's, the same for every dataset that makes Harbor tasks with f2p and p2p tests (section 5, "Harbor tasks"); provisioning the machine itself (creating it, the network, the first user and SSH key) and every credential, which the user or the machine's own provisioning places; joining a tailnet, signing in to any account, and the config and services of fleet and fednet, of which the setup installs the programs and nothing more; logging the machine into model accounts, since model traffic goes through redcoast, an account gateway developed as a separate project, and the machine holds no model login; merging PRs, cross-machine messaging, and model or effort policy.

## 2. Parts and how they connect

```text
  data machine
  ------------------------------------------------------------------
  machine/bootstrap.sh -> Ansible (machine/playbook.yml)
    installs uv, Docker, zsh, gh, herdr, Claude Code, gateway client,
    Node.js, Google Chrome, CJK fonts, Tailscale, op, direnv, fleet, fednet,
    atb, statute, Pi, Codex CLI, ripgrep, fd-find

  redcoast GitHub Release  ------>  gateway client (shim `claude` + redcoast-client)

  every `claude` in a pane -> shim -> redcoast-client -> redcoast -> model

  dataset repo
  ------------------------------------------------------------------
  pyproject.toml: dataforge @ git+https://github.com/Luolc/dataforge@<sha>#subdirectory=python
  its State subclasses (transitions, caps) -> dataforge.curation.Machine.run
    -> Actions: agent, script (on Host or Docker), trial (HarborRunner); fan_out
    -> ResourcePool (memory reservations shared by every process of the machine)
  gateway, if any: dataforge.gateway or its own, through the hooks
  dataforge queue serve -> each job (a command) from its queues, as caps and memory allow
```

The setup in `machine/` runs once per machine and again for upgrades. The gateway shim is first on `PATH` in every zsh (invariant 5), so a `claude` started in a shell goes through it; the setup passes no token. It also sets Docker's log rotation in `/etc/docker/daemon.json`, merged with the keys already there, and restarts dockerd when that changes the file, which stops the containers then running (`machine/README.md`, step 2). It writes the agent user's dotfiles, the zsh files, oh-my-zsh and powerlevel10k, and its keys in Claude Code's settings, from the chezmoi source in `machine/dotfiles/` with a chezmoi of its own (invariant 7).

15. `HarborRunner` passes Harbor only its listed variables and the dataset's `env`, removes everything with the trial's label after each run, and raises when anything is left; when `run` is interrupted, Harbor and its children are stopped before the files are given back, and a member of its process group that outlives Harbor is killed too, on the timeout path as well; the context `setup` returns, called with the trial's task directory, agent, limits and output directory, is entered before the overlay is written and left after that cleanup, also when Harbor exits non-zero or the cleanup fails, and the `TrialSetup` it yields reaches the overlay, Harbor's environment and its compose files. Before the files are given back, every container, whatever its labels, with a mount whose source is under the output directory is removed, and `run` raises when one is left; after the cleanup, each symlink in a trial's directory that resolves, or may, outside that directory, and each entry there that is no regular file, directory or symlink, is removed and named in `harbor.log`, so the trial `run` returns leads no reader to a host file, and its `agent` or `verifier` is given as an artifact only when it is a directory, not a symlink. ## 5. The state machine

An attempt makes one data item. It is a sequence of visits to states, starting at the first state given to `Machine(states, *, guard=None, on_step=None, max_cost_usd=None, deliverables=None)`, which checks that state names are unique, every `Goto` target exists, every `max_visits` is at least 1 and each deliverable is well formed (see "The record"); `machine.run(root)` runs one attempt. A state is a `State(name, transitions, max_visits=1, on_exhausted="failed", *, feedback=None, max_cost_usd=0.0)`; a dataset declares its states in a file (see "The declaration") and subclasses `State` only for what a declaration cannot say:

`run(ctx) -> Outcome(name, data, last=False, feedback=None)` does the state's work, usually through the actions below; `data` is a dict that converts to JSON, `feedback` a dict of the variables of the state's `feedback` template; `transitions` maps each outcome name to `Goto(state, report=True, mark=None, end_on_last_visit=False)` or `End(status)`. Each state chooses where to go; the machine knows no state's name, and this repo holds no dataset's table; `max_visits` caps how many times the state is entered in one attempt; `on_exhausted` is the status when that cap ends it with no mark. `max_cost_usd` is the most one visit may spend, which the machine's cost cap counts (see "Ending an attempt").

A `Goto` with `report=True` hands the target state `ctx.report`, a `Report(from_state, outcome, data, artifacts)`, whose text the dataset renders, unless the machine does: when the outcome gives `feedback` and the state a `feedback` template (a `string.Template` that also sees `${state}`, `${visit}` and `${round}`), the machine first renders it into the visit's `feedback.md`, the output `feedback`, recorded as an action of kind `report` (invariant 9). A `mark` (for example `too_easy`) records that the item as this visit left it may be kept if the attempt ends without passing. `last=True` says the state is not to be entered again; `end_on_last_visit=True` says not to take the `Goto` from a visit after which the state cannot be entered again (its `max_visits`-th, one with `last=True`, or one after which every chain of `Goto`s from the target back to the state passes a state that cannot be entered once more), since nothing could come back to it; it is meant for a `Goto` that leads back to its own state, as on one that cannot the first visit already ends the attempt. A dataset may subclass `Machine` too: `guard(ctx, state)` and `on_step(attempt)` are its methods, which by default call the callables it was given. `machine.graph()` returns the states and their transitions as data that `json.dumps` takes as is, `{start, states: [{name, kind, max_visits, on_exhausted, max_cost_usd}], edges: [{from, outcome, to, end, report, mark, end_on_last_visit}]}` (the TypedDicts `Graph`, `GraphState`, `GraphEdge`), and `mermaid(graph)` renders that as a Mermaid flowchart; `graph()` reads only the states' public attributes, and neither runs anything.

### The states it ships

A dataset configures them or subclasses them. Each takes the bound `Actions`, `rename` (a new name per outcome, applied last), `feedback` and `max_cost_usd`, and maps its result to an outcome through `outcome(ctx, result)` (`outcomes(ctx, results)` for `PassAtKState`), which a subclass may override, as it may each method that reads `ctx`:

| State | Runs | Default outcomes |
| -- | -- | -- |
| `AgentState(..., actions, env=HOST, spec=None, report_prompt=None, report_outputs=(), last_if_unresumable=False)` | `actions.agent` on `spec(ctx)` | `ok`, `failed` (outputs, answer or validator fail; feedback `{details}`), `error` (the run failed; invariant 11), with data `{ending, fixes, cost_usd}` |
| `ScriptState(..., actions, env=HOST, spec=None)` | `actions.script` on `spec(ctx)` | `ok`, `failed` (feedback `{details}`, the log) |
| `TrialState(..., actions, task_dir, agent, limits)` | one `actions.trial` | `solved`, `unsolved`, `error` (`TrialResult.exception` is set) |
| `PassAtKState(..., actions, task_dir, agent, limits, k, judge=None)` | k trials, `trial-0` to `trial-<k-1>`, through `fan_out`, then the `judge`, if any, on them | `all_solved`, `none_solved`, `in_range`, `error` (invariant 14), with data `{solved, errors, k}`, or the judge's verdict |
| `TrialsState(..., actions, task_dir, agents, limits, configs=None, each_task=False, judge=None)` | `agents[name]` trials of each agent, `<name>-<i>`, through `fan_out`; with `each_task`, on each subdirectory of `task_dir`, `<name>-<subdir>[-<i>]`; then the `judge`, if any, on them | `ok`, `error` (invariant 14), with each trial's `{rewards, exception}`, or the judge's verdict |
| `JudgeState(..., actions, judge)` | `actions.judge` on its spec's inputs | the verdict's |
| `RubricState(..., actions, reviews, env=HOST, workdir=None, resume=False, reuse_unchanged=False, cross_criteria=False)` | each `Review(name, rubric, inputs, notes)` at once, an agent with no tools, in its own session with `resume` (invariant 14) | `pass`, `fail` (feedback `{details}`: each review that did not pass, in order, under `### <name>`, with its findings), `error` (invariant 14; the same feedback, a review whose run failed giving `<name> returned no verdicts (<ending>).`), with each review's `{ending, cost_usd, passed, failed, verdicts}`; every visit also writes `rubric.json` (`rubric_table`: `{passed, reviews: [{name, passed, ending, call, resumed, reused, changed, criteria: [{criterion, passed, note, fix}]}]}`), `report.md` (`rubric_report`: a table per review and a line on what failed) and `<review>.inputs.json` (`rubric.Call`: its number, the text of each input block as the prompt gave it, how many versions each note's artifact had, the verdicts, the ending, `reused`, `resumed` and `changed`), recorded as one `report` action. The report holds a reviewer's words: render it as untrusted, with no raw HTML, no image loaded on its own and a link opened only when a person clicks it |

`spec(ctx)` returns the spec given, and on a visit that got a report adds `report_outputs` to its `outputs` and sets them as its `fresh_outputs` (invariant 11); `AgentState` renders its prompt, or `report_prompt` when the visit got a report, as a `string.Template` with `${state}`, `${visit}`, `${round}` and `${feedback}`, the text of the report's `feedback` output, leaving unknown placeholders and a lone `$` as they are. With `last_if_unresumable`, an outcome after which the session cannot go on has `last=True`. `task_dir` is a path, an input name (see "Actions") or a function of `ctx`. [`test_states.py`](../python/tests/test_states.py): `test_agent_state_renders_its_prompts_and_gives_feedback`, `test_last_if_unresumable_closes_the_state`, `test_script_state_runs_the_spec_it_is_given`, `test_a_trial_state_takes_an_artifact_or_a_path_in_it`.

A rubric is a TOML file: `system` and `[[criteria]]` with `id`, `question` and optional `check`, `pass_if` and `fail_if`; a criterion that gives a `severity` makes the file not a rubric, and `Rubric.load` raises `ValueError` naming the field. A review's prompt is the system text, each input as a tagged block (a directory as its files, other kinds by name and size, each cut at 40000 characters), the review's `notes` (a map of block tag to artifact name, the author's account) and the criteria, and with `cross_criteria` `rubric.CROSS_CRITERIA` and an `<other_criteria>` block of the other reviews' criteria; a re-review adds `rubric.REREVIEW`, which asks the reviewer to judge every criterion again on the whole of the inputs, treats the notes as a claim to check against the diffs and has it say why when it fails unchanged content it passed (invariant 14); its answer, one verdict per criterion in `rubric.VERDICTS_SCHEMA`, fails it when any criterion fails or has none. Each state's class attribute `OUTCOMES` names the outcomes its default `outcome` gives, before `rename`; `JudgeState`'s is `None`, its judge deciding ([`test_states.py`](../python/tests/test_states.py): `test_each_state_names_the_outcomes_it_gives`). A state's `possible_outcomes()` names what it may give after `rename`, its judge's `outcomes` for `JudgeState` and a `PassAtKState` or `TrialsState` with a `judge`, or `None` when it cannot say, as `State`'s does. `configs` maps a `TrialsState` agent's name to the agent it runs, when the name is not itself one. [`test_states.py`](../python/tests/test_states.py): `test_each_state_names_the_outcomes_it_may_give_after_rename`, `test_trials_state_runs_on_each_task_of_a_directory`, `test_a_judge_state_takes_its_verdict_on_earlier_outputs`; [`test_loader.py`](../python/tests/test_loader.py): `test_a_trials_state_may_take_a_judge`, `test_a_rubric_reads_resume_reuse_unchanged_cross_criteria_and_notes`, `test_rubric_fields_of_the_wrong_type_name_the_field` (a rubric state's `resume`, `reuse_unchanged`, `cross_criteria` and `notes`, a wrong type naming its path); [`test_rubric.py`](../python/tests/test_rubric.py): `test_every_review_passing_passes`, `test_a_review_sees_its_rubric_and_its_inputs`, `test_a_failed_review_fails_with_its_findings`, `test_any_criterion_that_fails_or_has_no_verdict_fails_the_review`, `test_failed_reviews_give_their_findings_in_order`, `test_a_bad_rubric_or_a_repeated_name_is_an_error`, `test_a_rubric_that_still_gives_a_severity_is_an_error`. `solved(result)` accepts a trial without an exception whose `reward` is at least 1.0; a subclass may change it, and how trials with an exception count, through `outcomes`.

### The declaration

The declaration of a dataset's states belongs to the dataset and lives in its repo: a YAML file that `load(source, *, inputs, actions, bindings=None, base_dir=None, guard=None, on_step=None, stack=None)` reads into a `Machine`, start state first, with PyYAML's safe loader (schema version 1, in the docstring of `dataforge.curation.loader`). Each state `uses` a shipped state (`agent`, `script`, `judge`, `trial`, `pass-at-k`, `trials`, `rubric`) or a `State` subclass the dataset registers in `bindings`, its table of names to Python objects; a state's `env` and `runner` name one of the declaration's `environments`, each a `Docker` as data, or `runners`, each a Claude Code `Runner`, a `HarborRunner` or what a registered factory gives, else a binding. A hook, what only Python can be (`post_start`, `serve`, `setup`, a mount's source), is `{binding: <name>}` or `{uses: <name>, with: {...}}`, the factory called with that data as it loads; an environment variable is only named, its value coming from the environment (`pass_env`) or a binding (`env`), a runner's `command` is a binding, a hook's `with` and `labels` are plain data that hold no credential, and each Docker environment is entered into `stack`, whose closing removes its container. `with` holds the state's arguments and `transitions` (not `on`, which YAML 1.1 reads as `true`) maps each outcome to a `goto` or an `end`. The top-level `deliverables` maps each name, in order, to its `kind`, `title`, `source` (`state`, `output` and `visit`, written as a literal `kept`, `last` or integer, not as an input) and, as its kind takes them, `table`, `value` (`field` and `output`) and `match`, the fields of `Deliverable`, `Source` and `Value` (see "The record"). Loading substitutes only `${{ inputs.<name> }}` and the declaration's `vars` as `${<name>}`, with no expressions or conditions, escaping an input's `$` in the texts the engine renders again, and leaves the engine's and the outcomes' variables to the engine; preparing and finishing an attempt and batches stay in the dataset's code, and the gateway is wired in through bindings, `dataforge.gateway`'s or its own. A declaration that breaks a check raises `SpecError` with the path of what is wrong (invariant 25), and `dataforge check <file> --inputs <json file> [--bindings <module>:<name>]` loads one with `Actions()` and starts nothing; `dataforge graph`, with the same arguments and `--format json|mermaid`, loads it the same way and prints `machine.graph()` as JSON or rendered by `mermaid`; `dataforge redeliver <file> <record>... [--not-ended <word>]... [--write]`, with the same `--inputs` and `--bindings`, loads it the same way and gives each record of an ended attempt the deliverables it declares now (see "The record").

### Actions

The machine (`dataforge.curation.engine`) knows no action; the actions (`dataforge.curation.actions`) reach it only through the context's `claim`, `resolve` and `record`, so a dataset may also call them from its own `run`. A dataset binds them once, `actions = Actions(agent_runner, trial_runner, pool)`; they write their outputs to the visit's directory `ctx.outdir`, whose names are unique within the visit.

What runs and where it runs are apart. An environment is `Host()` or `Docker(image, mounts, outputs, cpus, cpu_shares, memory_gb, memory_swap_gb, pids, network, labels, security, cap_drop, user, workdir, env, pass_env, pre_start, post_start)`. `docker create` gets `security` as `--security-opt`, `cap_drop`, `user` and `workdir` as the options of those names, `memory_swap_gb` as `--memory-swap` (memory plus swap) and each name in `pass_env` as a bare `--env`, so its value comes from docker's own environment, not its command line; an unset one is left out ([`test_actions.py`](../python/tests/test_actions.py): `test_docker_create_args`). A `Docker` environment is a container the dataset opens with `with Docker(...) as env:`; it is created on first use, started for the actions in it and stopped when none runs, so it keeps its files across visits, and removed when the `with` block exits. Inputs, outputs and the validator are copied in and out of it; the container's `user` may be non-root (invariant 18). With `outputs`, a writable `Mount`, every action writes its outputs straight into that mount, which keeps them across visits, as a session resumed across visits needs; each visit's outputs get a copy of it made on the host (invariant 19). An input names an artifact, or, when no artifact has that name, `"<artifact>/<path>"` names a path in one, which `Docker` stages under the same relative path; either may start with `"<state>:"` for the latest version a visit of that state wrote, since several states may write one name (`verdict.json`, `feedback`); or it is a `Path`; `optional_inputs` are left out when they do not exist yet. `agent` and `script` return `ActionResult(status, outputs, log, value, cost_usd, run, validation, fixes)`, the last three an agent's last run, its validator's last host run and its fixes ([`test_actions.py`](../python/tests/test_actions.py): `test_inputs_name_paths_in_artifacts_and_may_be_optional`, `test_a_path_in_an_artifact_is_staged_in_docker`, `test_an_input_may_name_the_state_that_wrote_it`):

- `actions.agent(ctx, spec, env)` runs an `AgentSpec`, a headless coding agent: `prompt`, `workdir`, `inputs`, `outputs`, `tools`, an optional `output_schema` (whose parsed reply is `value`), an optional `validator` with `max_fixes`, `name`, which a runner may use, `optional_inputs`, `fresh_outputs` (invariant 11), `session`, the key of the session a start goes on with, and `resume_prompt`, what it is asked when its start resumes a session, in place of `prompt`. The agent gets a copy of the validator, mode 0555, at a fixed path, `/dataforge/validator/<name>` in a `Docker` environment and `validators/<state>/<visit>/<action>/<name>` under the attempt's root on the host, and the prompt tells it to make it pass; the host then reruns its own original on the outputs (invariant 11). A rubric judge is an agent with no tools and an `output_schema`.
- `actions.script(ctx, spec, env)` runs a `ScriptSpec`, a command with its inputs as paths, and passes when it exits 0. A script on the host that declares `memory_gb` reserves it from the pool, for heavy host work such as an image build. A validator is an executable that takes the output directory and then the input paths as its arguments. A script, and a judge, also gets `DATAFORGE_SUMMARY`, a path where it may write Markdown for the record, which `Host` and `Docker` give and an `Env` of a dataset's own need not (`Staged.summary`); the whole file stays at `summary_path(ctx, index)`, `summaries/<state>/<visit>/<index>/summary.md` under the root, and the record keeps up to `SUMMARY_LIMIT`, 1 MiB (invariant 9).
- `actions.judge(ctx, judge, inputs)` runs a `Judge(spec)`, a script on the host, with `inputs` after its spec's and `DATAFORGE_ROOT`, `DATAFORGE_STATE`, `DATAFORGE_VISIT`, `DATAFORGE_ROUND` and `DATAFORGE_RECORD` (`<root>/records/<state>/<visit>.json`, `Attempt.to_json()` so far) besides `DATAFORGE_OUTPUTS`. It must exit 0 and write `verdict.json`, `{"outcome": str, "data": {...}, "feedback": {str: str} | null}`, and returns a `Verdict(outcome, data, feedback)`; otherwise, or when `Judge(spec, outcomes)` names the outcomes it may give and the verdict's is not one, it raises `JudgeError` (invariant 14; [`test_actions.py`](../python/tests/test_actions.py): `test_a_judge_gives_only_the_outcomes_it_names`).
- `actions.trial(ctx, name, task_dir, agent, limits)` runs one trial of a task: it starts the task's environment within `Limits(memory_gb, cpus)`, runs the agent (`nop`, `oracle` or an agent's configuration) and its verifier, and returns `TrialResult(rewards, exception, cost_usd, seconds, artifacts)`; its files become the artifact `name`.
- `fan_out(calls)` runs each zero-argument call at once, each in its own thread, and returns their results in the order given.

Agents run through the dataset's `AgentRunner`: `start(spec, task, env)`, where `task` is `AgentTask(prompt, inputs, outdir, validator, resume_prompt)` with the prompt and the resume prompt as the actions extend them and paths as `env` sees them, and `resume(session, prompt)` return `AgentRun(session, status, cost_usd, trace, result, ending, resumable, trace_format, resumed)`, `ending` how the run ended in the runner's words, `resumable` whether the session can go on and `resumed` whether it went on with the session of an earlier run, not a new one, and an optional `close(session)` runs after the action. The session is the runner's own object. A runner that can go on in another process also has `checkpoint(session)`, which gives as JSON data what it needs of a session, recorded as the action's `session` once the action's last run returned, and `restore(points)` ("Resuming an attempt"). `dataforge.runtime.claude.Runner` is one for Claude Code ("The Claude Code runner" below), and a dataset may give its own. Trials run through a `TrialRunner`, `run(task_dir, agent, limits, outdir)` and `memory_gb(limits)`, the memory a trial reserves, and a dataset may give its own; `run` returns a `TrialResult` whose optional `id`, `path`, `trace` and `trace_format` name the trial, its directory and the agent's trace, and `actions.trial` records them as the action's `TrialRecord`, keeping a path only when it is inside the trial's output directory (the directory then falling back to that one). `HarborRunner(harbor, ...)` implements it by running the Harbor CLI at the path it is given, so the package does not depend on Harbor. Given a `verifier`, the import path (`module:Class`) of a Harbor verifier class, it passes Harbor `--verifier` with it, so that a dataset takes over the step in which Harbor reads the trial's reward, such as reading it without following a link; without one, Harbor runs its own verifier ([`test_harbor.py`](../python/tests/test_harbor.py): `test_harbor_gets_the_verifier_only_when_one_is_set`). Given an `environment`, it passes Harbor `--env` with it, a type of Harbor's or an import path; `DOCKER_ENVIRONMENT` names `dataforge.curation.harbor_env`'s `DockerEnvironment`, Harbor's Docker environment without the probe, a container run with a 30 s timeout, by which Harbor's own refuses a no-network task when the Docker daemon is slow; a kernel that cannot load the sidecar's rules still fails the trial, as the sidecar never becomes healthy, and only Harbor imports that module (invariant 16). A trial Harbor did not start is run again (invariant 15). Harbor runs with an empty environment plus `HOME`, `PATH`, `DOCKER_HOST`, `DOCKER_CONFIG`, `HARBOR_TELEMETRY=0`, the dataset's `env` and the sidecar's limits, and is stopped with its children, SIGTERM for up to 30 s and then SIGKILL, past `timeout`, counted over all the runs of one trial, and when `run` is interrupted by any `BaseException`, such as `SystemExit` or `KeyboardInterrupt`; an interrupt during that grace period kills it at once; Harbor is gone before the files are given back and the cleanup runs, and once it has exited, its process group gets one more SIGKILL, so that a member that outlives it, such as a `docker compose up` started after the SIGTERM, is killed too, on the timeout path as well; `run` then raises the interrupt unchanged (the later one, when a second came during the grace period). Two risks stay open: a create request the Docker daemon accepted before the kill can still finish after the cleanup has listed the containers, and the container of a separate verifier environment carries no trial label, since Harbor builds that environment without the overlay. A compose overlay caps the task's container (every capability dropped, `no-new-privileges`, `pids`, `cpus`, `cpu_shares` and the trial's memory) and labels each of the trial's containers, networks and images with `dataforge.trial=<id>`; after the run every container that mounts from under the output directory, including those Harbor starts without the label (a separate verifier's), is removed, the trial's files are given back to this user, everything with the label is removed, and the trial's directory loses each symlink leading out of it and each entry that is no regular file, directory or symlink (invariant 15). When the task has its own `environment/docker-compose.yaml`, the runner reads its `main` service with `docker compose config --no-interpolate`, and the overlay leaves out each `cap_drop` or `security_opt` item `main` already has, since compose rejects a `security_opt` item that appears twice (invariant 17). The overlay leaves the container's network to `task.toml` and Harbor, which routes it through its egress sidecar unless a compose file names its network. When Harbor starts that sidecar, the overlay caps it at `Sidecar(cpus=0.5, memory_mb=64)` and 64 processes, and Harbor's environment carries the two limits as `DATAFORGE_SIDECAR_CPUS` and `DATAFORGE_SIDECAR_MEMORY_MB` for a task's own compose file (invariant 16). `HarborRunner.memory_gb` adds the sidecar's memory to the task's, whether or not the task has a sidecar; image builds and the cleanup's container are not reserved, so a dataset leaves the pool some headroom. A trial's `id` is Harbor's trial directory name and its `path` that directory. Its `trace` is the first file of the table `TRACES` that is a regular file in its `agent/`, not a symlink, since the agent's container writes it, and `trace_format` is that entry's format, in this order: `agent/claude-code.txt` as `claude-code-stream-json` (`claude -p --output-format stream-json`), `agent/pi.txt` as `pi-json` (`pi --mode json`) and `agent/codex.txt` as `codex-exec-jsonl` (`codex exec --json`); with none, both are None ([`test_harbor.py`](../python/tests/test_harbor.py): `test_a_trial_gives_its_name_directory_and_claude_code_trace`, `test_a_trial_gives_its_pi_or_codex_trace_and_the_cost_it_gives`, `test_a_trace_that_is_a_symlink_is_not_given`, `test_a_pi_trace_that_is_a_symlink_is_neither_given_nor_read`). Its `cost_usd` is `agent_result.cost_usd` from Harbor's `result.json` ([`test_harbor.py`](../python/tests/test_harbor.py): `test_harbors_cost_comes_before_the_pi_traces`); when that is not a number, it is read from that trace only when it is at most `TRACE_LIMIT`, 64 MiB: for Claude Code the `total_cost_usd` of the last `result` event, for Pi the sum of `usage.cost.total` over the assistant `message_end` events, which is Pi's own price list and not what was charged, and for Codex 0, since it gives none; a trial with neither, and one whose trace is not read, counts 0, which the attempt's cost cap then does not count ([`test_harbor.py`](../python/tests/test_harbor.py): `test_a_trials_cost_falls_back_to_the_claude_code_trace`, `test_a_trace_that_is_a_symlink_gives_no_cost`, `test_a_trace_over_the_limit_gives_no_cost`). `dataforge.runtime.pi` and `dataforge.runtime.codex` each have `TRACE_FORMAT`, a `Trace` and `read_trace(path)`, which counts the lines that are not JSON instead of failing on them and reads a missing file as empty: Pi's `Trace` gives the cost, the input and output tokens and the last assistant message's `stopReason` and text ([`test_pi.py`](../python/tests/test_pi.py): `test_a_trace_gives_the_cost_tokens_and_last_answer`, `test_a_cost_that_is_no_number_is_not_counted`), Codex's the last turn's ending, `completed` or `failed`, the last `agent_message` text and the tokens summed over `turn.completed` ([`test_codex.py`](../python/tests/test_codex.py): `test_a_trace_gives_the_tokens_and_last_answer`, `test_a_failed_turn_is_the_ending`); the `turn.completed` and `agent_message` shapes follow Codex's documented events and were not seen in a run, and the trial's trace and cost do not depend on them. No runner for Pi or Codex exists: a dataset runs them through Harbor's `pi` and `codex` agents, behind the gateway those of `dataforge.gateway.harbor` ("The gateway"). `HarborRunner` reads only the trial's top-level `result.json` and that trace, not the per-step results Harbor keeps for a multi-step trial.

### The Claude Code runner

`dataforge.runtime.claude` knows Claude Code and no dataset, gateway or credential: it runs the command and environment the caller gives, `claude` on the host or a prefix that runs it elsewhere.

- `Session(command, model, effort, max_budget_usd, thinking_display, timeout, persist, env)` and `run(name, prompt, *, run_dir, cwd, tools, allow, schema, add_dirs, resume)` run one `claude -p` session with stream-json output, its prompt on stdin, in safe mode with no settings, MCP servers or slash commands, restricted to its working directory and `add_dirs`, with only the tools given and the uses `allow` names (`dontAsk` denies the rest), an optional `--json-schema` and always `--max-budget-usd` and `--thinking-display` (`thinking_display`: `summarized` by default, or `omitted` or `highlights`; any other value is refused). The prompt, trace, stderr and usage go to `run_dir/<name>.*`. A new session starts in a new directory; past `timeout` its process group on this machine is killed; one not kept (`persist`) has its directory under `<config>/projects` removed when it ends, and a kept one leaves it to `remove_project_dir` (invariant 22). `run` returns `Result(subtype, session_id, cost_usd, output, text, rejected, paths, turns)`, `turns` the result event's `num_turns`; `read_trace(path)` returns a `Trace` of any stream-json, a trial's agent log included: its last result event, with the subtype, session ID, cost, turns, structured output and text, the lines that are not JSON and the last rejected output.
- `Runner(session, files, *, tools, add_dirs, continue_session, min_fix_usd, serve, spent)` is an `AgentRunner`. On `Host` it runs `session.command`, in `Docker` the same after `docker exec -i -w <workdir> <container>`; a timeout there leaves `claude` in the container to `Docker.stop`. The tools are the spec's, else the runner's; `Write` and `Edit` are allowed only in the workdir and the output directory, which the file tools may read with each input's directory and `add_dirs`. On the host a session's directory is the one `files` gives for the start that began it, and its paths must be absolute. Each start has one spend cap that its fixes share (invariant 23). The answer is the result's text, or with `output_schema` its structured output as JSON, whose absence fails the run (invariant 24). `files(spec, task, start, fix)` places each run's files, `numbered(run_dir, prefix)` as `<prefix>-<n>[-fix-<k>]`, with the spec's `name`, if any, for `prefix`; each run's `ending` is the result's subtype and `resumable` whether it ended with `success` and an ID ([`test_claude.py`](../python/tests/test_claude.py): `test_a_run_tells_its_ending_and_a_named_spec_names_its_files`); with `continue_session` each start resumes the session of the one before, for an attempt that keeps one session over its visits; a start with a `session` key resumes the session of the last start with that key, each key having a session of its own, and asks the task's `resume_prompt` (else its prompt), the key winning over `continue_session`, which then leaves `current` alone; give one key one start at a time, different keys may run at once; `serve` is entered around each run, where a dataset serves its gateway; `last` is how the last run ended. Its trace's format is `claude-code-stream-json`. `checkpoint(session)` gives `{id, total_usd, number, on_host, cwd}`, and for a keyed session also `session`, the key, and `subtype`, how its last run ended; `restore(points)` numbers starts on after the highest `number`, makes the session of the latest start of each key its key's and, with `continue_session`, that of the latest unkeyed start `current`, each with its total, so the next start passes `--resume <id>` and counts what the total grew by since (invariant 23). `close` keeps a keyed session, `end` removes those and `current`.

### The gateway

`Docker`, `HarborRunner` and the Claude Code runner do not know the model gateway; a dataset wires one in through their hooks: extra `mounts`; `env` variables, which `HarborRunner` sets both in the task's container and for the Harbor process; for `Docker`, a host-side `pre_start` called with the environment before each start and `post_start` after it, which may start a forwarder in the container with `exec` (invariant 20); for `HarborRunner`, `compose_overlay` files applied after its own and `setup`, called with the trial's task directory, agent, limits and output directory, so that it can serve the gateway for an agent's trial only, whose context spans the trial from before the overlay is written to after the cleanup and yields a `TrialSetup(mounts, env, compose_overlay)` added to that trial's own (invariant 15); and a `Runner`'s `serve`, entered around each run. `dataforge.gateway` ([`gateway/`](../python/src/dataforge/gateway/__init__.py)) replaces the gateways datasets keep in their own code, and a dataset may use it in place of its own; it is wired in through these hooks only, and nothing else in dataforge imports it, so a dataset that does not use it installs, imports and runs as before (invariant 30). It serves redcoast's two channels, `Channel.CLAUDE` for Claude Code and `Channel.CODEX` for Pi and Codex CLI (not `CODEX` the `Client`, the default for Codex CLI's), to containers with no network (`network_mode: none` for a trial's `main`, no `network` for a `Docker` environment), whose code then holds no credential. `serve(channel, socket, *, address=None, spend=None, ledger=None, timeout=60.0)` serves one gateway session on a Unix socket for the length of its block: the socket, made anew by each `serve`, has mode 0666, so that a container's user without `CAP_DAC_OVERRIDE` can connect, and its directory, which `serve` makes mode 0700 when it is missing and never removes, keeps the host's other users out. It starts redcoast-client as the launcher, `redcoast-client claude` (`Channel.CLAUDE`) or `redcoast-client pi` (`Channel.CODEX`), with `HOME`, `PATH` and the launcher's own variables only, and has it start this interpreter as the client, running the proxy (`python -I -m dataforge.gateway.proxy --channel <channel> --socket <path> --parent <pid>`, with the pause, the ledger and the cap as they are given), in a session of its own,, so that the session is only in the launcher's and the proxy's environments (`ANTHROPIC_BASE_URL` and `CLAUDE_CODE_OAUTH_TOKEN`, or `CODEX_GATEWAY_TOKEN` and the base URL in `$PI_CODING_AGENT_DIR/models.json`); the session ends when the proxy does, and the proxy when the process that started it does. The address and the machine credential's file are the `address=` and `credential_file=` lines of `~/.config/redcoast-client/shim.env` (`CLAUDE`) or of `codex.env` beside it (`Channel.CODEX`), read as the shim reads them; a caller may give `address` instead, the credential file then coming from the channel's file, else from `shim.env`. The proxy forwards only `POST /v1/messages` and `POST /v1/messages/count_tokens` (`Channel.CLAUDE`) or `POST /backend-api/codex/responses` (`Channel.CODEX`), with the session's `Authorization` in place of the request's and `Accept-Encoding: identity`, passes `Content-Encoding` and the body's bytes on unchanged, since Pi compresses its bodies, and sends a chunked body whole with its length. It reads each such body first (`screen`), decompressed as its `Content-Encoding` says (`gzip`, `deflate` or `zstd`), as UTF-8 JSON with no repeated key, and refuses a call that would have the model's side reach the network or run code for the container: a tool, wherever a `tools` list sits (`additional_tools`, a `namespace`), whose type is not one its client runs, by allow-list (no `type` or `custom` for `Channel.CLAUDE`; `function`, `custom`, `namespace`, `local_shell` and a `tool_search` the client executes for `Channel.CODEX`), `mcp_servers` or `container`, an image or document `source` other than `base64`, `text`, `content` or `file`, or an `image_url` or `file_url` other than a `data:` URL; and a body it cannot read (415 for an unknown encoding, 413 past 64 MiB decompressed, else 400). It answers 400 with the API's JSON error and logs `gateway: refused a model call: <tool type or field>` (invariant 26).

Inside `pausing(backoff)` the proxies of each channel in every process of the machine share one `Pause`, kept in `pause/<channel>.json` of the state directory ("Scheduling") under a lock and written whole by a rename: a 429 holds every call of that channel, waits and sends it again, and a session the gateway refuses for its quota pauses them too, until the earliest recovery the refusal names. Each process sets the `Backoff` as it enters; the rest of the pause outlives it. `Backoff(start_s=60.0, max_s=900.0, factor=2.0, limit_s=None)` sets the pauses: the first lasts `start_s`, each 429 that comes once a pause is over `factor` times the one before, up to `max_s` and at least the 429's `Retry-After`, and any other answer ends the run of pauses, as does `LAPSE_S` (900 s) after a pause ended with no 429 or refusal; the pause stops for good once the run has lasted `limit_s`, or after `REFUSALS` (3) quota refusals in a row each once a pause was over, and stays stopped, for every process and later blocks, until `Pause.clear()` or `pausing(backoff, clear=True)`, for work a person starts again, clears it. A block raises `QuotaError` as it ends when the pause stopped, or when its calls were paused `CUT_S` (360 s, about how long Claude Code waits for an answer) or longer and the pause is still under way; inside `sessions(limit)` at most `limit` proxies of each channel run at once on the machine, each holding a lease in `sessions/<channel>/` of the state directory, as the gateway caps a machine's sessions per channel (invariant 27). `Spend(prices, max_usd)` caps a session, which Pi and Codex CLI cannot do themselves: `prices` maps each model to a `Price(input, output, cache_read, cache_write_5m, cache_write_1h)` in US dollars per million tokens, which the caller gives. The proxy reads the usage of each 200 reply to `POST /v1/messages` or `POST /backend-api/codex/responses` as it passes it on, whatever its `Content-Type`: of a reply with `data:` events, from `message_start` and the last `message_delta` (`Channel.CLAUDE`) or from the `response` of `response.completed`, `response.done`, `response.incomplete` or `response.failed` (`Channel.CODEX`); of a reply without any, read as JSON, from its top-level `model` and `usage`, the message or the response itself; a reply with a `Content-Encoding` is not read, a reply that has no usage is logged to stderr as one line, `gateway: a reply without usage: <n> bytes, Content-Type <value>, events <type,type,...>, data lines <n>, first line <n> bytes, keys <a,b,...>, read as <mode>, first field <name>`, which holds the bytes read, the raw value of the reply's `Content-Type` header quoted as Python's `repr` quotes it (`none` when it has none), the distinct event types in order of first appearance, the number of lines that open with `data:`, the length of the first line that is not blank, its top-level keys when it parses as a JSON object (at most 8, each shown only if it is 1 to 32 letters, digits, `_`, `.` or `-`, else `?`; `none` otherwise), how the reply was read (`stream` or `json`) and the field name before the colon on a stream's first line (at most 16 bytes of letters, digits, `_` and `-`, `''` for a comment line, `?` for anything else, `-` for JSON) and nothing else of the body or the headers, and every reply, whatever its `Content-Type` (`text/event-stream`, `application/json`, any other or none), is looked at line by line for a `data:` event, however it opens, is an event stream once one line opens with `data:`, and is read whole as JSON only when it ends with no such line, so a reply that opens with a line of JSON and goes on as an event stream is read as one. `Channel.CLAUDE`'s `cache_creation_input_tokens` without the 5-minute and 1-hour split are priced at `cache_write_1h`. `Channel.CODEX`'s `input_tokens` hold its `input_tokens_details.cached_tokens`, priced as cache reads, and `input_tokens_details.cache_write_tokens`, when given, priced at `cache_write_5m`, the rest at `input`, and its `output_tokens` hold the reasoning; the proxy adds the reply's price to the session's spend, and once that reaches `max_usd`, or after a reply it cannot price (no usage, or a model `prices` lacks), it refuses every later request with 403 and, once no reply is under way, ends the session, so the spend may pass the cap by what the replies then under way cost (invariant 28). The cap adds to the trial's timeout and Pi's `max_turns`, which the dataset sets, and to Claude Code's `--max-budget-usd`, which caps only `claude`. With `ledger`, the proxy appends to it a JSON line per such reply, `{at, channel, model, usage, cost_usd, reason}`, `cost_usd` null with the `reason` when it could not price it (with no `Spend`, always, `reason` "no prices"), written whole and synced before it goes on, and `{at, channel, capped}` when the cap ends the session; `read_ledger(path)` reads it back, for a dataset's own accounts.

In the container, `forward.py`, which needs only Python 3.8 and imports nothing, so that it is mounted into any image as one file at `/opt/dataforge/forward.py`, copies each connection to `127.0.0.1:8787` byte for byte to the socket `/run/dataforge/model.sock`, in the directory `/run/dataforge` that the container mounts; the client there reaches the model only through that port and holds placeholders, `CLAUDE_ENV` (for `Channel.CLAUDE`: the port as `ANTHROPIC_BASE_URL`, a placeholder `CLAUDE_CODE_OAUTH_TOKEN` and the switches redcoast-client sets) or `CODEX_ENV` (for `Channel.CODEX`: `CODEX_GATEWAY_TOKEN`, a fixed unsigned JWT-shaped string whose `https://api.openai.com/auth` claim holds the `chatgpt_account_id` Pi requires, `PI_CODING_AGENT_DIR=/tmp/harbor-pi-agent`, the directory Harbor's `Pi` itself uses, and `PI_OFFLINE=1`). A `Client(path, version, sha256, program=None)` is what the container runs, `program` being a tarball's program inside it, checked against its sha256 before it is used: the executable of Claude Code at `~/.local/share/claude/versions/<version>`, mounted at `/usr/local/bin/claude`, or the release tarball of Pi or Codex CLI at `~/.local/libexec/<name>/<version>.tar.gz`, both as the machine setup keeps them, `CLAUDE_CODE`, `PI` and `CODEX`, the defaults, giving the versions and sha256 of `machine/versions.yml`, and a dataset may give its own; a tarball is unpacked once per process, with `tarfile`'s `data` filter, into a directory of the gateway's own (under `root` for `bindings`), whose whole package is mounted read-only at `/opt/dataforge/<name>`, with a one-line `/usr/local/bin/<name>` that runs its program (`/opt/dataforge/pi/pi/pi` for Pi, `/opt/dataforge/codex/bin/codex` for Codex CLI), so that Pi finds its assets and Codex CLI its `rg` and helpers (invariant 29). `trial_setup(*, spend=None, ledger=None, clients=None)` is a `HarborRunner` `setup` that, for an agent whose import path names one of `dataforge.gateway.harbor`'s, serves its channel for the trial, with the socket in a directory mode 0711 under the trial's own temporary directory, and yields that directory (mounted, since the cap replaces the socket by another file, which a mounted socket file would not follow), the forwarder, the client, the env, which also holds `DATAFORGE_CLIENT_VERSION`, the client's pinned version, and an overlay that gives `main` `network_mode: none` and a command that starts the forwarder and sleeps, so the task's image needs `python3`, and for Pi glibc, `grep` and `stdbuf`, which Harbor's `Pi` command runs; `bindings(root, *, prices=None, ledger=None, clients=None)` gives a declaration the same parts for a `Docker` environment, under `dataforge-gateway/`, and checks and unpacks each client when it is called, so that it raises there: `socket-dir`, a directory mode 0711 inside a 0700 one under `root`, made once, which the environment mounts at `/run/dataforge` and every `serve` reuses, `forwarder`, and `client/<name>` for each client of `clients` (default `claude-code`, `pi` and `codex`), the mount sources, `claude-env` and `codex-env`, `start-forwarder`, a `post_start` that starts the forwarder and waits until it listens, and `serve`, a factory whose `with` is `{channel, max_usd}` (`max_usd` optional, priced by `prices`), for a `Runner`; the serves of one socket take turns, each waiting while another's block runs. `dataforge.gateway.harbor`, which only Harbor imports, by import path, in its own process where the dataset installed it, holds Harbor 0.24.0's `ClaudeCode`, `Pi` and `Codex`, whose `populate_context_post_run` reads nothing under `agent/`, which the running container can point at a host file through a link (the trial's trace and cost come from `HarborRunner`, "Actions"). Each one's `install` runs nothing over the network and fails unless the client's `--version` gives the version in `DATAFORGE_CLIENT_VERSION`, which `trial_setup` sets; `Pi.install` also writes `models.json` and `settings.json` in `PI_CODING_AGENT_DIR` (mode 0700, the files 0600) by one command in the container, as the agent's user, since Harbor's own writer copies the file in and chmods it as root, which a container with every capability dropped refuses ([`test_harbor.py`](../python/tests/gateway/test_harbor.py): `test_pi_points_its_provider_at_the_forwarder`), `models.json` with `openai-codex`'s `baseUrl` `http://127.0.0.1:8787/backend-api` and `apiKey` `${CODEX_GATEWAY_TOKEN}`, and `settings.json` with `{"transport": "sse"}`, so that Pi does not first try the WebSocket transport, and `Codex`'s configuration is redcoast-client's, over the dataset's: `model_provider="gateway"` with `base_url` `http://127.0.0.1:8787/backend-api/codex`, `wire_api="responses"`, `env_key="CODEX_GATEWAY_TOKEN"` and `supports_websockets=false`, and the other settings redcoast-client passes, with `web_search="disabled"` under the dataset's, since Codex CLI declares the hosted web search by default for some models ([`test_harbor.py`](../python/tests/gateway/test_harbor.py): `test_codex_declares_no_web_search_unless_the_dataset_asks`). Harbor is a development dependency of dataforge only, for these agents' tests.

### Scheduling

A `ResourcePool(memory_gb, max_running=None)` is shared by every attempt and action of every process of the machine, attempts running in threads or processes and a visit's actions running concurrently. Each reservation is a lease (`dataforge.leases`) in `memory/` of the state directory, `dataforge.statedir.state_dir()`: `DATAFORGE_STATE_DIR` when set and not empty, else `$XDG_STATE_HOME/dataforge` when that is absolute, else `~/.local/state/dataforge`. A lease is a file its holder keeps an exclusive `flock` on; the kernel lets go of it when the holder's process ends, SIGKILL too, and the next reader removes the lease, so the reservation is returned, though the containers the process started run on until something stops them. Each pool holds what all the leases hold to its own `memory_gb` and `max_running`; processes that share a state directory give the same ones. Before a `Docker` environment starts, a trial runs (its runner's `memory_gb`) or a host script with `memory_gb` runs, it reserves its memory limit, waiting while the pool lacks it, and returns it when it stops or fails to start (invariant 13). Each action holds one reservation at most (a script in a `Docker` environment runs under the environment's), so no two wait on each other. CPUs are shared by each container's `cpus` cap and `cpu_shares` weight, not reserved. The pool counts whole MiB, so a fraction of a GB is returned as it was taken. Creating a pool larger than the machine's `MemAvailable` plus what the leases hold raises `ValueError`, and so does a reservation larger than the pool. Jobs reach the machine through `dataforge.queue`. A dataset project's queue file names its queues and how many jobs of each may run at once, how many may run on the machine, the `MemAvailable` a start must leave and the highest 1-minute load at which one starts. The jobs are rows of one SQLite file in WAL mode, by default under `queue/` of the state directory: each a command (an argv, run without a shell), a directory, the memory it declares, an optional dedup key, opaque labels and its state, `queued`, `running`, then `done`, `failed` or `canceled`; the rows of ended jobs stay. `dataforge queue serve` claims queued jobs in one `BEGIN IMMEDIATE` transaction as invariant 31 allows, the oldest of each queue first, a running job holding the memory it declared less its session's resident memory, never below 0; it reads neither the pool's leases nor the gateway's pause, and a job's actions reserve from the pool as any others do. Each job runs under `python -m dataforge.queue.wrapper`, which leads a session of its own, runs the command with the scheduler's environment and writes its exit status, so a job outlives the scheduler, which knows the wrapper by its pid, starttime and boot ID. The claim writes the job's directory with its symbolic links resolved, in the same transaction, and the wrapper runs the command there: a job given a link, such as a `current` link to one of several releases of a dataset's code, stays on the release the link named as the job started, wherever the link points later, as far as its command reaches its code through its directory (a relative path), and its row says which release that is. The scheduler reads its queue file once, as it starts; restarting it is how a new version of it or of the queue file takes over, since the new scheduler kills no job, takes the running ones as they are, counts them in its caps and records their ends (invariant 31). A systemd unit that runs the scheduler needs `KillMode=process`, so that stopping it leaves the jobs running.

### Artifacts

Each attempt has a directory, the `root` the dataset gives. An action's outputs are stored under `artifacts/<state>/<visit>/<name>`. `ctx.artifacts.get(name)` returns the latest version of an artifact and `ctx.artifacts.history(name)` every version, oldest first. An action's inputs name artifacts or give paths; actions get them read-only.

### Ending an attempt

| Status | When |
| -- | -- |
| the `End` status | a transition reached `End(status)`, for example `passed` |
| the last mark | a state's visits were exceeded, it was entered again after `last=True`, a `Goto` with `end_on_last_visit` was not taken, or the cost cap or `guard` blocked it, and a `Goto` taken before (or that one) had a mark; `kept_visit` names the visit that `Goto` left |
| the state's `on_exhausted` | its visits were exceeded, it was entered again after `last=True`, or a `Goto` with `end_on_last_visit` was not taken, with no mark before |
| `budget` | the cost cap or `guard` blocked a state with no mark before |

Before each visit, after the `max_visits` check, the cost cap blocks it when the machine has a `max_cost_usd` and the state's `max_cost_usd` added to what the attempt's actions cost so far would pass it, so a visit that reaches the cap exactly is let in (within float rounding, since costs are summed as floats); `reason` and `stopped` then give what was spent, the state's worst case and the cap. Then `guard(ctx, state) -> str | None` runs; a reason blocks the visit. In the last three rows `reason` names the state, the visit and the cause. An exception is never turned into a status (invariant 12).

### The record

`run` returns an `Attempt`; `to_json()` gives `{status, reason, kept_visit, round, budget, final, visits, deliverables, graph, resumptions}`, `budget` being `{max_usd, cost_usd, stopped}`: the cap, what the recorded actions cost with each resumption's `carried_usd`, and the reason when the cap ended the attempt. Each visit is `{state, visit, round, outcome, data, mark, last, actions: [{kind, status, outputs, cost_usd, started_at, ended_at, summary, trace, session, trial}]}`, its `round` how many times the first state had been entered when it began (also `ctx.round`), `last` whether its outcome had `last=True`, and the top-level `round` the last visit's, times in UTC ISO 8601 (`isoformat()`, `+00:00`). An action's `trace` is `{path, format}` of an agent's first run or null, `session` its runner's checkpoint or null, and `trial` a trial's `{id, path, trace, rewards, exception}` or null, paths relative to the root. `Attempt.from_json(root, data)` reads a record back (invariant 12). `final` maps each state to its last visit up to the end, or up to `kept_visit` when the item is kept, pass@k's included. The machine writes no record file: it calls `on_step(attempt)` when a visit begins, after each `claim` and `record` of its actions, after the visit and when the attempt ends, one call at a time, so a record written from it holds the visit that runs, with `outcome` null and the actions recorded so far; the dataset decides where the record goes. `graph` is `machine.graph()`, so a reader can draw the machine and where the attempt went. `deliverables` lists what the dataset declared to show, in its order, resolved at each step as the attempt would end then: from the visits before the one that runs, but a `trials` deliverable that takes the running visit, which lists its trials that have started; `[]` before the first step and when a state's exception ends the attempt. A record keeps the deliverables declared when its attempt ran; `machine.deliverables_of(attempt)` resolves the machine's own in an attempt that has ended, from `Attempt.from_json`, and `dataforge redeliver` writes them into records: it prints, per record, `change`, `same`, `skip` or `error` (`wrote` with `--write`) and each deliverable that changes, then the count of each, replaces only the `deliverables` key, as the record was laid out, after copying the record to `<record>.<UTC time>.bak` beside it, which restores it when moved back, skips an attempt that has not ended as the viewer decides ([design-viz.md, section 4, "The project file"](design-viz.md#the-project-file)) and one whose last visit has no outcome, and exits 1 when the declaration does not load or a record cannot be read, such as one an older dataforge wrote that `Attempt.from_json` refuses, or written, the others handled all the same. A `Deliverable(kind, title, source, table=None, value=None, match=None)` takes a `Source(state, output=None, visit="kept")`, `visit` being `"kept"` (the state's last visit up to `kept_visit`, else its last), `"last"` or n for its n-th: kind `files` shows that output's files, `report` a Markdown output, with `table` a JSON output of the same results, and `trials` the trials of the visit, with no `output`, those whose output's name `match` matches, a glob (`fnmatch.fnmatchcase`, such as `regrade-[0-9]*`), or every one without it, and `value`, a `Value(field, output=None)`, the value at the keys `field` in a JSON output of the visit or, without `output`, in its outcome `data` (for `PassAtKState`, `Value(["solved"])`); a JSON output is read only when it is a regular file of at most `VALUE_LIMIT`, 1 MiB, else `value` is null with the `reason`. Each entry is `{name, kind, title, state, output, visit, visit_index, path, reason}`, `visit_index` its visit's place in `visits` and `path` relative to the root, or null with the `reason` when it was not reached; a report adds `table`, the same for its source; trials add `match`, `k`, how many trials it lists, `value`, `{output, field, value, reason}`, and `trials`, each `{id, output, path, trace, result}`, `trace` `{path, format}` or null and `result` `{reward, rewards, exception}`, `reward` the rewards' `"reward"`; a trial that has started and is not recorded yet has `id`, `trace` and `result` null. What the paths lead to is written by agents, the code under test and containers, so a reader renders it as untrusted content: Markdown with no raw HTML, no external image loaded on its own and a link opened only when a person clicks it, and a trace's text as text; and it opens a path without following symlinks, since an output copied out of a container may be one.

### Resuming an attempt

`machine.resume(record, *, carried_usd=0.0, discarded_path=None, reason=None)` goes on with an attempt whose process stopped, from `Attempt.from_json` of the last record `on_step` saw, in the same root. It leaves out the visits at the end whose outcome is null or `raised`, whose actions may not all have been recorded, rebuilds from the others how often each state was entered, the closed states and the artifacts, takes the last kept visit's transition again without writing its feedback again, or starts at the first state when none is kept, and runs on as `run` does under its own `max_cost_usd`; the left-out visits run again under their numbers, so the caller moves their outputs first if it keeps them. Each runner a state names (`State.runners()`, an action state's `agent_runner`) that has `restore` gets the `session` of every action of the record's visits of its states, the left-out ones included, in order. It raises `ResumeError` when the record's `status` is set, its `graph` is not `machine.graph()`, a visit names an unknown state or a kept one is numbered out of order, or the last kept visit's transition is missing, an `End` or a `Goto` with `end_on_last_visit` that ended the attempt (invariant 12). Each resumption adds to `resumptions` `{at, kept, discarded, carried_usd, reason}`: `kept` how many visits it kept, so the first `kept` of the final `visits` came before it and a later resumption's is never smaller; `discarded` each left-out visit as recorded, with `path`, the caller's `discarded_path` relative to the root, and `reason`, null unless `path` is null; `carried_usd` what ended calls spent that no kept visit's actions record, which the caller gives; `reason` why it stopped, as the caller says. A `Docker` environment takes the attempt's container with `adopt(container)` instead of creating one, and raises `ValueError` naming each item in which `docker inspect` shows it differ (invariant 18): the image, the network (none without `network`, not the host's with it), the binds, and the user, working directory and limits the env sets are the env's, the security options exactly `security`, and the labels and capability drops at least the env's; the container is not privileged, has no added capability, device, other mount or volumes from another container, and shares neither the host's nor another container's PID or IPC namespace nor the host's UTS, user or cgroup namespace, so where docker's default cgroup namespace is the host's (cgroup v1) none is adopted. What else the env leaves to docker, such as a read-only root, device cgroup rules, sysctls, ulimits, published ports or, with `network`, another container's network, and `env` and `pass_env` are not checked.

### Harbor tasks

**Planned, not built**, this whole subsection: `dataforge.task` and `dataforge.testrunner` replace what each dataset that makes Harbor tasks with f2p and p2p tests keeps in its own code, a `[metadata]` of loose top-level keys with one count table of the f2p tests alone and at most one principle as a string, and a harness that runs only pytest. Harbor leaves `task.toml`'s `[metadata]` unchecked and drops a top-level table it does not know, so a dataset's fields live under `[metadata]`. Its top level holds only `id` and `language`; `tests` maps each suite, `f2p` and `p2p`, to counts by kind, the unit a declared test (a manifest entry), not a case a parametrized test expands to, with `p2p.project` counting the project's own tests, which have no kind; `[[principles]]` lists `{id, text, type, source, tests}`, `id` unique (`p1`, `p2`, …), `type` `best_practice` or `trade_off`, `source` where the principle comes from or empty, and `tests` the refs of the tests that refer to it (`<suite>::<id>`, below), derived from the manifest; `instruction.settings` names the settings the task is given in, `implicit` (the principles kept from the solver) and `explicit` (stated to it). The kinds, which the dataset checks, and every other group, such as a `provenance` of where the task comes from, are the dataset's, kept as they are in `Metadata.extra` and not read. `parse_metadata(table)` gives a `Metadata(id, language, tests, principles, settings, extra)`, each principle a `Principle(id, text, type, source, tests)`, or raises `MetadataError` with the key path of what is wrong, as `metadata.principles[1].type`; a `[metadata]` with a `tests` table is of this format, one without of the format before. `metadata_toml(meta)` writes the section with the same bytes for equal data, dataforge's keys in a fixed order and the dataset's sorted, since an export's revision is a digest of the file. `public_toml(text, allow)` keeps only the keys whose dotted paths under `[metadata]` `allow` lists, a table by its path whole (`tests`, or `tests.f2p` alone) and an array of tables only whole, the rest of the file reading the same, so a key added later stays inside until a dataset lists it (one that exports `id`, `language` and `tests` gives what it gave before under the new names). `explicit_instruction(description, principles)` is, for one principle, `Guideline for your change: <text>`, `\n\n---\n\n`, the description stripped and a line end, the bytes datasets wrote before; for more, `Guidelines for your change:` and a line `- <text>` for each, in `id` order, before the same rule; the whole set is given at once, never a subset, and none is a `ValueError`. `principles_sha256` is, for one principle, the SHA-256 of its UTF-8 text, as datasets hashed it before; for more, of the texts in `id` order joined by `\n`, and since a principle's text holds no line break, no two sets give one string; with none, None. `parse_legacy(table, groups, principle_tests=())` reads the format before: `test_kinds`, which counted the f2p tests alone, as `tests.f2p`, with no `p2p`; `settings` as `instruction.settings`; `alignment`, with `difference`, as one principle `p1` whose `type` is the `difference` only when that is `best_practice` or `trade_off`, `source` empty and `tests` the `principle_tests` the dataset gives; no principle without `alignment`; `tags` and `difference` dropped; each other top-level key to the dotted path `groups` names for it, and one it does not name a `MetadataError`, so nothing is lost unsaid. Tasks and exports already written are not rewritten.

`dataforge.testrunner` is a package that imports only Python 3.12's standard library (`tomllib` among it), the same code on the host and, as `testrunner`, in a task: `files()` gives its files by their paths under a task's `tests/`, where a dataset writes them, so a task runs apart from its pipeline. The dataset's own harness, which restores files, applies the patch and writes `reward.json`, calls `testrunner.run`; one with no harness of its own runs `python -m testrunner` in `/tests`, which writes only `ctrf.json`. The manifest `tests/manifest.toml` lists `[[test]]` entries: `suite`, any non-empty name, `runner` (`pytest`, `jest`, `vitest`, `jasmine`, `go`, `cargo`, `maven` or `phpunit`), `id`, the runner's own ID of the test with paths from the project's root (a pytest node ID, `<file> > <describe> > … > <title>` for jest, vitest and Jasmine, `<import path>::<TestName>` for go, `<source file>::<libtest name>` for cargo, `<class>#<method>` for Maven and `<class>::<method>` for PHPUnit), and optionally `dir`, where under the root the runner starts (`.` by default), `kind` and `principle`, at most one principle's `id`; `[no_tests]` maps a suite with no test that can run to the reason, and such a suite lists none. A test is referred to as `<suite>::<id>` (`Test.ref`), in a principle's `tests` too, and no two entries share one. The manifest's check is of its shape and types, that refs and the `dest`s of phase 2's `[[file]]` are unique, that each `dest` stays inside the root, and, when a dataset passes its principles' IDs, that each `principle` is one of them; a dataset checks the kinds and the rules of its suites (such as which suite may have which kind) on what `load` returns. The tests of one runner and `dir` run in one call of the runner's native command there, with no network, and its native report (JUnit XML, `go test -json`, or libtest's text for cargo) becomes CTRF in `/logs/verifier/ctrf.json`, the file Harbor's own templates and viewer use, `specVersion` `0.1.0`, the version the specification's root page gives (read 2026-10-22), times in milliseconds: each case `{name, status, duration, suite, labels, message, trace, filePath}`, `name` the case's native ID (a parametrized case's `…[a]` among them), `status` `passed`, `failed` or `skipped`, `suite` `["<suite>"]`, `labels` `{id, runner, kind, principle}`, `id` the ref of the manifest entry the case belongs to, and a key without a value left out, never null; an error is `failed` with `rawStatus: "error"`, and a case the manifest does not list is not written. Every listed test must be in the report and pass: one the report lacks is written `failed`, `rawStatus: "error"`, `duration` 0, `name` its `id`, with the message `listed in the manifest but not in the runner's report`, so a solver that stops a runner from collecting a test fails it. `testrunner.ctrf.suite_counts(report)` gives `{suite: (passed, total)}`, only `passed` passing, from which the dataset writes its own keys of `reward.json`. `testrunner.runners.RUNNER_FILES` gives each runner's globs of the test configuration it loads on its own (`conftest.py` and `pytest.ini` for pytest, `jest.config.*` for jest), which the dataset's harness restores to the base and whose added files it deletes; a build file that is also test configuration (`pyproject.toml`, `setup.cfg`, `package.json`, `pom.xml`, `Cargo.toml`), which a fix may have to change, is not restored, and the harness takes the test configuration from the base's copy and hands it to the runner on its command line (pytest's `-c`, jest's `--config`), the check that every listed test is there covering the rest. Phase 1 runs the project's own tests, the `p2p` entries with no kind, and a dataset's pytest tests run as before, their results merged into the same `ctrf.json` through `testrunner.ctrf`.

Phase 2, designed with phase 1 and built after it, replaces the rest of the pytest-only harness: a dataset's pytest plugin that marks a test's kind, the reading of those marks from the source, and the pytest wrappers a session wrote around another framework's tests. A session writes its f2p and p2p tests in the project's own framework, as files of the task's `tests/` that the manifest places into the project's tree (`[[file]]`, `{source, dest}`, overwriting, through no link, and left there), and declares each test there with its `kind` and its `principle`, which the runner writes into `labels`; a dataset's static checks read the manifest, not the code. At test time, offline, the test files are copied to their places and the runner's own command runs in place, such as `cargo test --offline` in `dir` on the `target/` the image built, with `CARGO_TARGET_DIR` unchanged, so the project's own build compiles the tests, only what changed since the image, and no harness is compiled and no build directory copied; how a task of each language other than Python lays out its directories, what its image installs beforehand and how the dependency caches of Go, Rust and Node serve an eval with no network is an open question (section 6). So a Rust task whose test wrote a harness at test time and ran `cargo build` over a copy of a `target/` prebuilt in the image, tens of GB a run, has its tests compiled in place by `cargo test` instead, writing only what changed.

### What a dataset gives

Its declaration, in its own repo, with the bindings it names and the `State` subclasses for what it cannot say (or its states in Python, the states above configured or subclassed), with transitions, marks and caps; the attempt's root; its `Docker` environments; `Actions` bound to an `AgentRunner` when its states use agents, a `TrialRunner` (`HarborRunner` or its own) when they use trials, and the pool; the gateway wiring, `dataforge.gateway`'s or its own, if it needs one; the attempt's `max_cost_usd`, if it has a cap, and each state's; and optionally `guard`, for blocks other than the cost cap, and `on_step`.
