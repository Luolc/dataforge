# dataforge design

The current design, edited in place. Why a decision was made lives in the PR that made it. Only an orchestra-triggered design pass edits this file; other PRs describe their effect on it under "Design impact".

## 1. What this is, and what it is not

dataforge is the shared part of a "data machine": a small multi-agent workshop that builds datasets with coding agents (today Claude Code, the only supported agent). Each dataset lives in its own repo. This repo holds what every dataset repo shares:

- the machine setup that turns a fresh Ubuntu 24.04 machine into a data machine;
- the files every agent on the machine gets (the base `AGENTS.md`; section 6);
- a Python package, `dataforge` in `python/`, that dataset repos install; its module `dataforge.curation` holds the state machine that runs an attempt at one data item, the states and actions it ships, and a Harbor trial runner (section 5); its module `dataforge.runtime` runs coding agents headless, Claude Code through `dataforge.runtime.claude` (section 5, "The Claude Code runner").
- planned, not built: viz, a read-only web viewer of attempts, made of the module `dataforge.viz` and a frontend in `web/`; its design is [`design-viz.md`](design-viz.md).

Starting agents, carrying messages between them, tracking who owes work and flagging stuck agents belong to Agent Fleet, a separate project. The setup installs its `fleet` binary and the tools it calls (fednet, atb, statute), each at its latest release (invariant 2); configuring and running them is the machine's own provisioning (section 4).

How a dataset repo works, which dataforge supports but does not enforce:

- Whoever writes a change does not merge it. A separate agent reviews before merge.
- A change to the dataset-level acceptance criteria passes a two-arm regression: the reference sample scores full marks and an empty output fails. Per-item check scripts ship with the data and go through normal review.
- Specs (what to build, what counts as acceptable) are edited only by people.
- Runtime state lives on the machine under `~/scratch/<repo>/` and is never committed: `progress/<job>.log`, an optional `board.md`, and `lessons.md`, where any agent writes suggestions that become PRs.

Not in scope:

- Dataset-specific code and dependencies; they stay in the dataset's repo. That includes the states of the state machine and what each does: its prompts, validators, checks, rubrics, how pass@k is judged, its caps and the text of each report.
- Provisioning the machine itself (creating it, the network, the first user and SSH key), and every credential: the user or the machine's own provisioning places them.
- Joining a tailnet, signing in to any account, and the config and services of fleet and fednet: the setup installs those programs and nothing more.
- Logging the machine into model accounts. Model traffic goes through redcoast, an account gateway developed as a separate project; the machine holds no model login.
- Merging PRs, cross-machine messaging, and model or effort policy.

## 2. Parts and how they connect

```text
  data machine
  ------------------------------------------------------------------
  machine/bootstrap.sh -> Ansible (machine/playbook.yml)
    installs uv, Docker, zsh, gh, herdr, Claude Code, gateway client,
    Node.js, Google Chrome, CJK fonts, Tailscale, op, direnv, fleet, fednet,
    atb, statute

  redcoast GitHub Release  ------>  gateway client (shim `claude` + redcoast-client)

  every `claude` in a pane -> shim -> redcoast-client -> redcoast -> model
```

```text
  dataset repo
  ------------------------------------------------------------------
  pyproject.toml: dataforge @ git+https://github.com/Luolc/dataforge@<sha>#subdirectory=python
  its State subclasses (transitions, caps) -> dataforge.curation.Machine.run
    -> Actions: agent, script (on Host or Docker), trial (HarborRunner); fan_out
    -> ResourcePool (memory reservations shared by every attempt)
  gateway, if any: wired in through the Docker and HarborRunner hooks
```

The setup in `machine/` runs once per machine and again for upgrades. The gateway shim is first on `PATH` in every zsh (invariant 5), so a `claude` started in a shell goes through it; the setup passes no token. It also sets Docker's log rotation in `/etc/docker/daemon.json`, merged with the keys already there, and restarts dockerd when that changes the file, which stops the containers then running (`machine/README.md`, step 2).

## 3. Invariants

Each one links to the test that guards it. Test files: [`machine/tests/`](../machine/tests/) (setup in a clean container), [`.github/scripts/`](../.github/scripts/).

1. The setup is idempotent: a second run reports `changed=0`, and so does a run in check mode. [`machine/tests/inside.sh`](../machine/tests/inside.sh): "second run changed something", "check-mode run would change something". A run in check mode on a machine that lacks a vendor apt source added by a newer setup (here the Node.js one) still runs to the end: "check-mode run without the Node.js source". So does one on a machine where Chrome was never installed, which lacks `/opt/google-chrome`: "check-mode run before Chrome is installed".
2. Every third-party tool version is pinned in [`machine/versions.yml`](../machine/versions.yml) (Ubuntu archive packages follow the release); this covers Node.js and Google Chrome, and Chrome has no apt source, so `apt upgrade` cannot move it off its pin. The tools the repository owner publishes, statute, fleet, fednet, atb and the gateway client (redcoast-client and the shim), are not pinned there: each setup run installs the latest non-draft, non-prerelease release of the tool, statute's being the newest `statute-v*` one of a repository that releases more than statute, and verifies it against the checksum file in that release; when the release has none, it installs nothing and fails the setup, naming the tool. A fednet that upgraded itself to its latest release is left as it is; any other is replaced. [`machine/tests/inside.sh`](../machine/tests/inside.sh): the per-tool version checks, "statute: run reports …", "a release without its checksum file was accepted", "fednet replaced", and for the pins "a Chrome .deb with the wrong sha256 was accepted", "an apt source for Chrome: …".

## 4. Interfaces

- Setting up a data machine: [`machine/README.md`](../machine/README.md); settings in [`machine/playbook.yml`](../machine/playbook.yml), versions in [`machine/versions.yml`](../machine/versions.yml).
- The machine's own settings, which the setup reads and never writes: the GitHub token in `~/.config/dataforge/github-token`, the git identity and gateway address in `~/.config/dataforge/setup.yml`, and private environment variables in `~/.config/dataforge/zshenv.local`.
- Install paths that other setups may rely on: `/usr/local/bin/<name>` for `fleet`, `fednet`, `atb`, `statute`, `herdr` and `gh`; `/usr/bin/<name>` for `tailscale`, `op`, `direnv`, `node`, `npm`, `npx` and `google-chrome`.
- The Claude Code runner: the names section 5 gives of `dataforge.runtime.claude` ([`claude.py`](../python/src/dataforge/runtime/claude.py)).
- The state machine: `dataforge.curation` exports the names in its `__all__` ([`__init__.py`](../python/src/dataforge/curation/__init__.py)), among them the classes section 5 names. A dataset repo installs it from git, pinned to a commit of main whose CI run for the push succeeded on its first attempt; upgrading is changing that SHA. There is no tag and no package index release. Each runtime dependency is added with its reason in the PR that adds it.

## 5. The state machine

An attempt makes one data item. It is a sequence of visits to states, starting at the first state given to `Machine(states, *, guard=None, on_step=None, max_cost_usd=None, deliverables=None)`, which checks that state names are unique, every `Goto` target exists, every `max_visits` is at least 1 and each deliverable is well formed (see "The record"); `machine.run(root)` runs one attempt. A state is a `State(name, transitions, max_visits=1, on_exhausted="failed", *, feedback=None, max_cost_usd=0.0)`; a dataset declares its states in a file (see "The declaration") and subclasses `State` only for what a declaration cannot say:

- `run(ctx) -> Outcome(name, data, last=False, feedback=None)` does the state's work, usually through the actions below; `data` is a dict that converts to JSON, `feedback` a dict of the variables of the state's `feedback` template.
- `transitions` maps each outcome name to `Goto(state, report=True, mark=None, end_on_last_visit=False)` or `End(status)`. Each state chooses where to go; the machine knows no state's name, and this repo holds no dataset's table.
- `max_visits` caps how many times the state is entered in one attempt; `on_exhausted` is the status when that cap ends it with no mark. `max_cost_usd` is the most one visit may spend, which the machine's cost cap counts (see "Ending an attempt").

A `Goto` with `report=True` hands the target state `ctx.report`, a `Report(from_state, outcome, data, artifacts)`, whose text the dataset renders, unless the machine does: when the outcome gives `feedback` and the state a `feedback` template (a `string.Template` that also sees `${state}`, `${visit}` and `${round}`), the machine first renders it into the visit's `feedback.md`, the output `feedback`, recorded as an action of kind `report` (invariant 9). A `mark` (for example `too_easy`) records that the item as this visit left it may be kept if the attempt ends without passing. `last=True` says the state is not to be entered again; `end_on_last_visit=True` says not to take the `Goto` from a visit after which the state cannot be entered again (its `max_visits`-th, one with `last=True`, or one after which every chain of `Goto`s from the target back to the state passes a state that cannot be entered once more), since nothing could come back to it; it is meant for a `Goto` that leads back to its own state, as on one that cannot the first visit already ends the attempt. A dataset may subclass `Machine` too: `guard(ctx, state)` and `on_step(attempt)` are its methods, which by default call the callables it was given. `machine.graph()` returns the states and their transitions as data that `json.dumps` takes as is, `{start, states: [{name, kind, max_visits, on_exhausted, max_cost_usd}], edges: [{from, outcome, to, end, report, mark, end_on_last_visit}]}` (the TypedDicts `Graph`, `GraphState`, `GraphEdge`), and `mermaid(graph)` renders that as a Mermaid flowchart; `graph()` reads only the states' public attributes, and neither runs anything.

### The states it ships

A dataset configures them or subclasses them. Each takes the bound `Actions`, `rename` (a new name per outcome, applied last), `feedback` and `max_cost_usd`, and maps its result to an outcome through `outcome(ctx, result)` (`outcomes(ctx, results)` for `PassAtKState`), which a subclass may override, as it may each method that reads `ctx`:

| State | Runs | Default outcomes |
| -- | -- | -- |
| `AgentState(..., actions, env=HOST, spec=None, report_prompt=None, last_if_unresumable=False)` | `actions.agent` on `spec(ctx)` | `ok`, `failed` (outputs, answer or validator fail; feedback `{details}`), `error` (the run failed; invariant 11), with data `{ending, fixes, cost_usd}` |
| `ScriptState(..., actions, env=HOST, spec=None)` | `actions.script` on `spec(ctx)` | `ok`, `failed` (feedback `{details}`, the log) |
| `TrialState(..., actions, task_dir, agent, limits)` | one `actions.trial` | `solved`, `unsolved`, `error` (`TrialResult.exception` is set) |
| `PassAtKState(..., actions, task_dir, agent, limits, k, judge=None)` | k trials, `trial-0` to `trial-<k-1>`, through `fan_out`, then the `judge`, if any, on them | `all_solved`, `none_solved`, `in_range`, `error` (invariant 14), with data `{solved, errors, k}`, or the judge's verdict |
| `TrialsState(..., actions, task_dir, agents, limits, configs=None, each_task=False)` | `agents[name]` trials of each agent, `<name>-<i>`, through `fan_out`; with `each_task`, on each subdirectory of `task_dir`, `<name>-<subdir>[-<i>]` | `ok`, `error` (invariant 14), with each trial's `{rewards, exception}` |
| `JudgeState(..., actions, judge)` | `actions.judge` on its spec's inputs | the verdict's |
| `RubricState(..., actions, reviews, env=HOST, workdir=None)` | each `Review(name, rubric, inputs)` at once, an agent with no tools | `pass`, `fail` (feedback `{details}`: each review that did not pass, in order, under `### <name>`, with its findings), `error` (invariant 14; the same feedback, a review whose run failed giving `<name> returned no verdicts (<ending>).`), with each review's `{ending, cost_usd, passed, failed, warnings, verdicts}`; every visit also writes `rubric.json` (`rubric_table`: `{passed, reviews: [{name, passed, ending, criteria: [{criterion, severity, passed, note, fix}]}]}`) and `report.md` (`rubric_report`: a table per review and a line on what failed), recorded as a `report` action. The report holds a reviewer's words: render it as untrusted, with no raw HTML, no image loaded on its own and a link opened only when a person clicks it |

`spec(ctx)` returns the spec given; `AgentState` renders its prompt, or `report_prompt` when the visit got a report, as a `string.Template` with `${state}`, `${visit}`, `${round}` and `${feedback}`, the text of the report's `feedback` output, leaving unknown placeholders and a lone `$` as they are. With `last_if_unresumable`, an outcome after which the session cannot go on has `last=True`. `task_dir` is a path, an input name (see "Actions") or a function of `ctx`. [`test_states.py`](../python/tests/test_states.py): `test_agent_state_renders_its_prompts_and_gives_feedback`, `test_last_if_unresumable_closes_the_state`, `test_script_state_runs_the_spec_it_is_given`, `test_a_trial_state_takes_an_artifact_or_a_path_in_it`.

A rubric is a TOML file: `system` and `[[criteria]]` with `id`, `severity` (`error` or `warning`), `question` and optional `check`, `pass_if` and `fail_if`. A review's prompt is the system text, each input as a tagged block (a directory as its files, other kinds by name and size, each cut at 40000 characters) and the criteria; its answer, one verdict per criterion in `rubric.VERDICTS_SCHEMA`, fails it when an `error` criterion fails or has none. Each state's class attribute `OUTCOMES` names the outcomes its default `outcome` gives, before `rename`; `JudgeState`'s is `None`, its judge deciding ([`test_states.py`](../python/tests/test_states.py): `test_each_state_names_the_outcomes_it_gives`). A state's `possible_outcomes()` names what it may give after `rename`, its judge's `outcomes` for `JudgeState` and a `PassAtKState` with a `judge`, or `None` when it cannot say, as `State`'s does. `configs` maps a `TrialsState` agent's name to the agent it runs, when the name is not itself one. [`test_states.py`](../python/tests/test_states.py): `test_trials_state_runs_on_each_task_of_a_directory`, `test_a_judge_state_takes_its_verdict_on_earlier_outputs`; [`test_rubric.py`](../python/tests/test_rubric.py): `test_every_review_passing_passes`, `test_a_review_sees_its_rubric_and_its_inputs`, `test_a_failed_review_fails_with_its_findings`, `test_failed_reviews_give_their_findings_in_order`, `test_a_bad_rubric_or_a_repeated_name_is_an_error`.

`solved(result)` accepts a trial without an exception whose `reward` is at least 1.0; a subclass may change it, and how trials with an exception count, through `outcomes`.

### The declaration

The declaration of a dataset's states belongs to the dataset and lives in its repo: a YAML file that `load(source, *, inputs, actions, bindings=None, base_dir=None, guard=None, on_step=None, stack=None)` reads into a `Machine`, start state first, with PyYAML's safe loader (schema version 1, in the docstring of `dataforge.curation.loader`). Each state `uses` a shipped state (`agent`, `script`, `judge`, `trial`, `pass-at-k`, `trials`, `rubric`) or a `State` subclass the dataset registers in `bindings`, its table of names to Python objects; a state's `env` and `runner` name one of the declaration's `environments`, each a `Docker` as data, or `runners`, each a Claude Code `Runner`, a `HarborRunner` or what a registered factory gives, else a binding. A hook, what only Python can be (`post_start`, `serve`, `setup`, a mount's source), is `{binding: <name>}` or `{uses: <name>, with: {...}}`, the factory called with that data as it loads; an environment variable is only named, its value coming from the environment (`pass_env`) or a binding (`env`), a runner's `command` is a binding, a hook's `with` and `labels` are plain data that hold no credential, and each Docker environment is entered into `stack`, whose closing removes its container. `with` holds the state's arguments and `transitions` (not `on`, which YAML 1.1 reads as `true`) maps each outcome to a `goto` or an `end`. The top-level `deliverables` maps each name, in order, to its `kind`, `title`, `source` (`state`, `output` and `visit`, written as a literal `kept`, `last` or integer, not as an input) and, as its kind takes them, `table` and `value` (`field` and `output`), the fields of `Deliverable`, `Source` and `Value` (see "The record"). Loading substitutes only `${{ inputs.<name> }}` and the declaration's `vars` as `${<name>}`, with no expressions or conditions, escaping an input's `$` in the texts the engine renders again, and leaves the engine's and the outcomes' variables to the engine; preparing and finishing an attempt, batches and the gateway stay in the dataset's code. A declaration that breaks a check raises `SpecError` with the path of what is wrong (invariant 25), and `dataforge check <file> --inputs <json file> [--bindings <module>:<name>]` loads one with `Actions()` and starts nothing; `dataforge graph`, with the same arguments and `--format json|mermaid`, loads it the same way and prints `machine.graph()` as JSON or rendered by `mermaid`.

### Actions

The machine (`dataforge.curation.engine`) knows no action; the actions (`dataforge.curation.actions`) reach it only through the context's `claim`, `resolve` and `record`, so a dataset may also call them from its own `run`. A dataset binds them once, `actions = Actions(agent_runner, trial_runner, pool)`; they write their outputs to the visit's directory `ctx.outdir`, whose names are unique within the visit.

What runs and where it runs are apart. An environment is `Host()` or `Docker(image, mounts, outputs, cpus, cpu_shares, memory_gb, memory_swap_gb, pids, network, labels, security, cap_drop, user, workdir, env, pass_env, pre_start, post_start)`. `docker create` gets `security` as `--security-opt`, `cap_drop`, `user` and `workdir` as the options of those names, `memory_swap_gb` as `--memory-swap` (memory plus swap) and each name in `pass_env` as a bare `--env`, so its value comes from docker's own environment, not its command line; an unset one is left out ([`test_actions.py`](../python/tests/test_actions.py): `test_docker_create_args`). A `Docker` environment is a container the dataset opens with `with Docker(...) as env:`; it is created on first use, started for the actions in it and stopped when none runs, so it keeps its files across visits, and removed when the `with` block exits. Inputs, outputs and the validator are copied in and out of it; the container's `user` may be non-root (invariant 18). With `outputs`, a writable `Mount`, every action writes its outputs straight into that mount, which keeps them across visits, as a session resumed across visits needs; each visit's outputs get a copy of it made on the host (invariant 19). An input names an artifact, or, when no artifact has that name, `"<artifact>/<path>"` names a path in one, which `Docker` stages under the same relative path; either may start with `"<state>:"` for the latest version a visit of that state wrote, since several states may write one name (`verdict.json`, `feedback`); or it is a `Path`; `optional_inputs` are left out when they do not exist yet. `agent` and `script` return `ActionResult(status, outputs, log, value, cost_usd, run, validation, fixes)`, the last three an agent's last run, its validator's last host run and its fixes ([`test_actions.py`](../python/tests/test_actions.py): `test_inputs_name_paths_in_artifacts_and_may_be_optional`, `test_a_path_in_an_artifact_is_staged_in_docker`, `test_an_input_may_name_the_state_that_wrote_it`):

- `actions.agent(ctx, spec, env)` runs an `AgentSpec`, a headless coding agent: `prompt`, `workdir`, `inputs`, `outputs`, `tools`, an optional `output_schema` (whose parsed reply is `value`), an optional `validator` with `max_fixes`, `name`, which a runner may use, and `optional_inputs`. The agent gets a copy of the validator, mode 0555, at a fixed path, `/dataforge/validator/<name>` in a `Docker` environment and `validators/<state>/<visit>/<action>/<name>` under the attempt's root on the host, and the prompt tells it to make it pass; the host then reruns its own original on the outputs (invariant 11). A rubric judge is an agent with no tools and an `output_schema`.
- `actions.script(ctx, spec, env)` runs a `ScriptSpec`, a command with its inputs as paths, and passes when it exits 0. A script on the host that declares `memory_gb` reserves it from the pool, for heavy host work such as an image build. A validator is an executable that takes the output directory and then the input paths as its arguments. A script, and a judge, also gets `DATAFORGE_SUMMARY`, a path where it may write Markdown for the record, which `Host` and `Docker` give and an `Env` of a dataset's own need not (`Staged.summary`); the whole file stays at `summary_path(ctx, index)`, `summaries/<state>/<visit>/<index>/summary.md` under the root, and the record keeps up to `SUMMARY_LIMIT`, 1 MiB (invariant 9).
- `actions.judge(ctx, judge, inputs)` runs a `Judge(spec)`, a script on the host, with `inputs` after its spec's and `DATAFORGE_ROOT`, `DATAFORGE_STATE`, `DATAFORGE_VISIT`, `DATAFORGE_ROUND` and `DATAFORGE_RECORD` (`<root>/records/<state>/<visit>.json`, `Attempt.to_json()` so far) besides `DATAFORGE_OUTPUTS`. It must exit 0 and write `verdict.json`, `{"outcome": str, "data": {...}, "feedback": {str: str} | null}`, and returns a `Verdict(outcome, data, feedback)`; otherwise, or when `Judge(spec, outcomes)` names the outcomes it may give and the verdict's is not one, it raises `JudgeError` (invariant 14; [`test_actions.py`](../python/tests/test_actions.py): `test_a_judge_gives_only_the_outcomes_it_names`).
- `actions.trial(ctx, name, task_dir, agent, limits)` runs one trial of a task: it starts the task's environment within `Limits(memory_gb, cpus)`, runs the agent (`nop`, `oracle` or an agent's configuration) and its verifier, and returns `TrialResult(rewards, exception, cost_usd, seconds, artifacts)`; its files become the artifact `name`.
- `fan_out(calls)` runs each zero-argument call at once, each in its own thread, and returns their results in the order given.

Agents run through the dataset's `AgentRunner`: `start(spec, task, env)`, where `task` is `AgentTask(prompt, inputs, outdir, validator)` with the prompt as the actions extend it and paths as `env` sees them, and `resume(session, prompt)` return `AgentRun(session, status, cost_usd, trace, result, ending, resumable)`, `ending` how the run ended in the runner's words and `resumable` whether the session can go on, and an optional `close(session)` runs after the action. The session is the runner's own object. `dataforge.runtime.claude.Runner` is one for Claude Code ("The Claude Code runner" below), and a dataset may give its own. Trials run through a `TrialRunner`, `run(task_dir, agent, limits, outdir)` and `memory_gb(limits)`, the memory a trial reserves, and a dataset may give its own; `run` returns a `TrialResult` whose optional `id`, `path`, `trace` and `trace_format` name the trial, its directory and the agent's trace, and `actions.trial` records them as the action's `TrialRecord`, keeping a path only when it is inside the trial's output directory (the directory then falling back to that one). `HarborRunner(harbor, ...)` implements it by running the Harbor CLI at the path it is given, so the package does not depend on Harbor. Harbor runs with an empty environment plus `HOME`, `PATH`, `DOCKER_HOST`, `DOCKER_CONFIG`, `HARBOR_TELEMETRY=0`, the dataset's `env` and the sidecar's limits, and is stopped with its children past `timeout`. A compose overlay caps the task's container (every capability dropped, `no-new-privileges`, `pids`, `cpus`, `cpu_shares` and the trial's memory) and labels each of the trial's containers, networks and images with `dataforge.trial=<id>`; after the run every container that mounts from under the output directory, including those Harbor starts without the label (a separate verifier's), is removed, the trial's files are given back to this user, everything with the label is removed, and the trial's directory loses each symlink leading out of it and each entry that is no regular file, directory or symlink (invariant 15). When the task has its own `environment/docker-compose.yaml`, the runner reads its `main` service with `docker compose config --no-interpolate`, and the overlay leaves out each `cap_drop` or `security_opt` item `main` already has, since compose rejects a `security_opt` item that appears twice (invariant 17). The overlay leaves the container's network to `task.toml` and Harbor, which routes it through its egress sidecar unless a compose file names its network. When Harbor starts that sidecar, the overlay caps it at `Sidecar(cpus=0.5, memory_mb=64)` and 64 processes, and Harbor's environment carries the two limits as `DATAFORGE_SIDECAR_CPUS` and `DATAFORGE_SIDECAR_MEMORY_MB` for a task's own compose file (invariant 16). `HarborRunner.memory_gb` adds the sidecar's memory to the task's, whether or not the task has a sidecar; image builds and the cleanup's container are not reserved, so a dataset leaves the pool some headroom. A trial's `cost_usd` is `agent_result.cost_usd` from Harbor's `result.json`; when that is not a number, it is the `total_cost_usd` of the last `result` event in the trial's `agent/claude-code.txt`, the Claude Code trace that Harbor's `claude-code` agent writes, read only when it is a regular file, not a symlink, of at most `TRACE_LIMIT`, 64 MiB; a trial with neither, such as one of another agent whose result has no cost, counts 0, and so does one whose trace is not read, which the attempt's cost cap then does not count ([`test_harbor.py`](../python/tests/test_harbor.py): `test_a_trials_cost_falls_back_to_the_claude_code_trace`, `test_a_trace_that_is_a_symlink_gives_no_cost`, `test_a_trace_over_the_limit_gives_no_cost`). Its `id` is Harbor's trial directory name, its `path` that directory, and its `trace` that `agent/claude-code.txt`, in the format `claude-code-stream-json` (`claude -p --output-format stream-json` as it printed it), only when it is a regular file and not a symlink, since the agent's container writes it ([`test_harbor.py`](../python/tests/test_harbor.py): `test_a_trial_gives_its_name_directory_and_claude_code_trace`, `test_a_trace_that_is_a_symlink_is_not_given`). `HarborRunner` reads only these two top-level places, not the per-step results Harbor keeps for a multi-step trial.

### The Claude Code runner

`dataforge.runtime.claude` knows Claude Code and no dataset, gateway or credential: it runs the command and environment the caller gives, `claude` on the host or a prefix that runs it elsewhere.

- `Session(command, model, effort, max_budget_usd, timeout, persist, env)` and `run(name, prompt, *, run_dir, cwd, tools, allow, schema, add_dirs, resume)` run one `claude -p` session with stream-json output, its prompt on stdin, in safe mode with no settings, MCP servers or slash commands, restricted to its working directory and `add_dirs`, with only the tools given and the uses `allow` names (`dontAsk` denies the rest), an optional `--json-schema` and always `--max-budget-usd`. The prompt, trace, stderr and usage go to `run_dir/<name>.*`. A new session starts in a new directory; past `timeout` its process group on this machine is killed; one not kept (`persist`) has its directory under `<config>/projects` removed when it ends, and a kept one leaves it to `remove_project_dir` (invariant 22). `run` returns `Result(subtype, session_id, cost_usd, output, text, rejected, paths)`; `read_trace(path)` returns a `Trace` of any stream-json, a trial's agent log included: its last result event, with the subtype, session ID, cost, turns, structured output and text, the lines that are not JSON and the last rejected output.
- `Runner(session, files, *, tools, add_dirs, continue_session, min_fix_usd, serve, spent)` is an `AgentRunner`. On `Host` it runs `session.command`, in `Docker` the same after `docker exec -i -w <workdir> <container>`; a timeout there leaves `claude` in the container to `Docker.stop`. The tools are the spec's, else the runner's; `Write` and `Edit` are allowed only in the workdir and the output directory, which the file tools may read with each input's directory and `add_dirs`. On the host a session's directory is the one `files` gives for the start that began it, and its paths must be absolute. Each start has one spend cap that its fixes share (invariant 23). The answer is the result's text, or with `output_schema` its structured output as JSON, whose absence fails the run (invariant 24). `files(spec, task, start, fix)` places each run's files, `numbered(run_dir, prefix)` as `<prefix>-<n>[-fix-<k>]`, with the spec's `name`, if any, for `prefix`; each run's `ending` is the result's subtype and `resumable` whether it ended with `success` and an ID ([`test_claude.py`](../python/tests/test_claude.py): `test_a_run_tells_its_ending_and_a_named_spec_names_its_files`); with `continue_session` each start resumes the session of the one before, for an attempt that keeps one session over its visits; `serve` is entered around each run, where a dataset serves its gateway; `last` is how the last run ended.

### The gateway

Neither `Docker` nor `HarborRunner` knows the model gateway: its client and credentials differ from machine to machine, and the machine setup already puts the gateway shim on `PATH` (invariant 5). A dataset wires it in through their hooks: extra `mounts`; `env` variables, which `HarborRunner` sets both in the task's container and for the Harbor process; for `Docker`, a host-side `pre_start` called with the environment before each start and `post_start` after it, which may start a forwarder in the container with `exec` (invariant 20); and for `HarborRunner`, `compose_overlay` files applied after its own and `setup`, called with the trial's task directory, agent, limits and output directory, so that it can serve the gateway for an agent's trial only, whose context spans the trial from before the overlay is written to after the cleanup and yields a `TrialSetup(mounts, env, compose_overlay)` added to that trial's own, such as the mount of a gateway socket it serves (invariant 15).

### Scheduling

A `ResourcePool(memory_gb, max_running=None)`, one per process, is shared by every attempt and action in it, attempts running in threads and a visit's actions running concurrently. Before a `Docker` environment starts, a trial runs (its runner's `memory_gb`) or a host script with `memory_gb` runs, it reserves its memory limit, waiting while the pool lacks it, and returns it when it stops or fails to start (invariant 13). Each action holds one reservation at most (a script in a `Docker` environment runs under the environment's), so no two wait on each other. CPUs are shared by each container's `cpus` cap and `cpu_shares` weight, not reserved. The pool counts whole MiB, so a fraction of a GB is returned as it was taken. Creating a pool larger than the machine's `MemAvailable` raises `ValueError`, and so does a reservation larger than the pool.

### Artifacts

Each attempt has a directory, the `root` the dataset gives. An action's outputs are stored under `artifacts/<state>/<visit>/<name>`. `ctx.artifacts.get(name)` returns the latest version of an artifact and `ctx.artifacts.history(name)` every version, oldest first. An action's inputs name artifacts or give paths; actions get them read-only.

### Ending an attempt

| Status | When |
| -- | -- |
| the `End` status | a transition reached `End(status)`, for example `passed` |
| the last mark | a state's visits were exceeded, it was entered again after `last=True`, a `Goto` with `end_on_last_visit` was not taken, or the cost cap or `guard` blocked it, and a `Goto` taken before (or that one) had a mark; `kept_visit` names the visit that `Goto` left |
| the state's `on_exhausted` | its visits were exceeded, it was entered again after `last=True`, or a `Goto` with `end_on_last_visit` was not taken, with no mark before |
| `budget` | the cost cap or `guard` blocked a state with no mark before |

Before each visit, after the `max_visits` check, the cost cap blocks it when the machine has a `max_cost_usd` and the state's `max_cost_usd` added to what the attempt's actions cost so far would pass it, so a visit that reaches the cap exactly is let in (within float rounding, since costs are summed as floats); `reason` and `stopped` then give what was spent, the state's worst case and the cap. Then `guard(ctx, state) -> str | None` runs; a reason blocks the visit. In the last three rows `reason` names the state, the visit and the cause. An exception is never turned into a status (invariant 12).

### The record

`run` returns an `Attempt`; `to_json()` gives `{status, reason, kept_visit, round, budget, final, visits, deliverables, graph}`, `budget` being `{max_usd, cost_usd, stopped}`: the cap, what the recorded actions cost and the reason when the cap ended the attempt. Each visit is `{state, visit, round, outcome, data, mark, actions: [{kind, status, outputs, cost_usd, started_at, ended_at, summary}]}`, its `round` how many times the first state had been entered when it began (also `ctx.round`), and the top-level `round` the last visit's, times in UTC ISO 8601. `final` maps each state to its last visit up to the end, or up to `kept_visit` when the item is kept, pass@k's included. The machine writes no record file: after each visit it calls `on_step(attempt)`, and the dataset decides where the record goes. `graph` is `machine.graph()`, so a reader can draw the machine and where the attempt went.

`deliverables` lists what the dataset declared to show, in its order, `[]` until the attempt ends and when a state's exception ends it. A `Deliverable(kind, title, source, table=None, value=None)` takes a `Source(state, output=None, visit="kept")`, `visit` being `"kept"` (the state's last visit up to `kept_visit`, else its last), `"last"` or n for its n-th: kind `files` shows that output's files, `report` a Markdown output, with `table` a JSON output of the same results, and `trials` every trial of the visit, with no `output`, and `value`, a `Value(field, output=None)`, the value at the keys `field` in a JSON output of the visit or, without `output`, in its outcome `data` (for `PassAtKState`, `Value(["solved"])`); a JSON output is read only when it is a regular file of at most `VALUE_LIMIT`, 1 MiB, else `value` is null with the `reason`. Each entry is `{name, kind, title, state, output, visit, visit_index, path, reason}`, `visit_index` its visit's place in `visits` and `path` relative to the root, or null with the `reason` when it was not reached; a report adds `table`, the same for its source; trials add `k`, how many trials it lists, `value`, `{output, field, value, reason}`, and `trials`, each `{id, output, path, trace, result}`, `trace` `{path, format}` or null and `result` `{reward, rewards, exception}`, `reward` the rewards' `"reward"`. What the paths lead to is written by agents, the code under test and containers, so a reader renders it as untrusted content: Markdown with no raw HTML, no external image loaded on its own and a link opened only when a person clicks it, and a trace's text as text; and it opens a path without following symlinks, since an output copied out of a container may be one.

### What a dataset gives

Its declaration, in its own repo, with the bindings it names and the `State` subclasses for what it cannot say (or its states in Python, the states above configured or subclassed), with transitions, marks and caps; the attempt's root; its `Docker` environments; `Actions` bound to an `AgentRunner` when its states use agents, a `TrialRunner` (`HarborRunner` or its own) when they use trials, and the pool; the gateway wiring, if it needs one; the attempt's `max_cost_usd`, if it has a cap, and each state's; and optionally `guard`, for blocks other than the cost cap, and `on_step`.
