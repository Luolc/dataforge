# dataforge viz design

The design of viz, the attempt viewer, kept apart from [`design.md`](design.md) for length; it follows the same conventions. **Planned, not built**: every part below is to be built in the phases of section 6, and once a part is built, a design PR moves it from section 6's list to the present tense, as for `design.md`; the PR that builds it describes its effect under "Design impact".

## 1. What this is, and what it is not

viz is a web viewer for the attempts a dataset runs on `dataforge.curation` (design.md section 5, ["The state machine"](design.md#5-the-state-machine)), and for the job queue of `dataforge.queue`. It shows, for each attempt, its record, the runs it made and the deliverables its declaration names, so that a person can see what a machine did and what it produced; it shows the queue's jobs, and puts a data item's actions in the queue and cancels a job, the only things it writes (invariant 1). It has two parts in this repo:

- a backend, the module `dataforge.viz` in the Python package, that reads attempt directories and their records and serves a JSON API and the frontend's files;
- a frontend in `web/`, a single-page app built with Vite, React, TypeScript, Tailwind and Radix, with every third-party library bundled, so it works with no network.

A dataset repo gives only configuration (section 4, "The project file"): where its attempts are, what its states and statuses are called and how they are coloured, how its attempts group into data items, the extra columns of its home page, its own tabs of Markdown files on the attempt page, and the actions a data item may be put in the queue for. The viewer knows no dataset: it picks a view only by a deliverable's `kind`.

Not in scope:

- Writing anything but the job queue: no comments, no tickets. The viewer never writes to an attempt directory (invariant 1).
- Running, resuming or stopping an attempt itself: an action puts the project file's command in the queue, whose scheduler runs it, and a cancel asks the queue to stop a job. A page shows what was on disk when it was read, and reads again by the browser's own reload or its refresh button; only while an attempt runs do its page and its project's home page read it again on their own, and its times go on, counted in the browser from the start its record gives (section 5, "Home page", "While it runs" and "Reading again").
- Sampling a machine: the Monitor page (section 5) only reads a database a dataset's own sampler writes.
- Deploying: the service unit, the machine, the network and its access rules belong to whoever runs the viewer; anyone who can reach the address can also queue the project files' actions and cancel the queue's jobs. A write is taken only from a page opened at `http://<listen.host>:<listen.port>` itself, the port left out at 80 (invariant 10), so a page opened at a name for that address, or through a tunnel or a proxy at another address, can read but not write. How the built frontend reaches a machine is an open question (section 7).
- Showing data to people outside: the read-only share site, a process of its own ([`design-share.md`](design-share.md)).

## 2. Parts and how they connect

```text
  browser: web/ (React SPA) --- GET /api/... (JSON, files as bytes) ---> dataforge.viz (FastAPI)
                               POST /api/... (two writes, invariant 10)         |
                               GET /<anything else> (the built web/dist)        |
                                                                                 v
     site file (listen, projects, queue) -> queue file -> dataforge.queue (its SQLite database)
                                         -> project files (one per dataset) -> attempt directories
                                                                         record file (Attempt.to_json())
                                                                         artifacts/, summaries/, trials
                                                      -> monitor.db (optional, SQLite, read-only)
```

`dataforge viz serve --config <site file> --static <dir>` starts one process. It reads the site file and each project file once at start and refuses to start when one fails its check (invariant 6); it then reads attempt directories, and a project's monitor database, on each request, with no cache. `<dir>` is the output of `npm run build` in `web/`. The frontend talks to the backend only through the API in section 4 and draws everything from the record as written.

## 3. Invariants

Each invariant links to the tests that guard it, in `python/tests/viz/` or next to the frontend module in `web/src/`; invariant 5 is also kept by review.

1. Read-only but for the queue: no route writes, creates, moves or deletes anything, under an attempt's root or elsewhere, and every route answers only `GET` and `HEAD`, any other method getting 405, but for the two writes of section 4, "The API", which answer only `POST` and write only to the job queue, through `dataforge.queue`: a submit adds one queued job, a cancel ends a queued job or asks a running one to end, and sends its process group SIGTERM; neither writes anything else, nor takes a command, a queue or a path from the request, nor an argument but the item's ID and a bounded number for each parameter the action declares (invariant 10). Tests: [`test_actions.py`](../python/tests/viz/test_actions.py): `test_an_action_queues_its_command_with_the_item_alone`, `test_an_action_s_parameters_go_into_its_command_as_flags`, `test_a_queued_job_is_canceled_by_its_id_alone`, `test_the_queue_s_reads_write_nothing`. One more exception: the monitor routes open `monitor.db`, and the queue's and the actions' GETs the queue's database, with SQLite's read-only URI (`file:<path>?mode=ro`), and SQLite, opening a WAL database so, creates the database's `-wal` and `-shm` files beside it when they are missing and writes to `-shm`, as every reader of a WAL database does; nothing else in that directory or elsewhere changes, and the directory must be writable for the reader. Tests: [`test_app.py`](../python/tests/viz/test_app.py): `test_every_route_is_a_get_and_writes_nothing`; for the monitor [`test_monitor.py`](../python/tests/viz/test_monitor.py): `test_the_monitor_routes_write_only_sqlite_s_own_files`, `test_the_database_is_opened_read_only`; for the queue `test_the_queue_s_reads_write_nothing` above.
2. No symlink is followed and no read leaves the attempt's root (its directory, as in design.md, ["Artifacts"](design.md#artifacts)), except that the item's `lock` file is `stat`ed, never read, from the item's directory: an attempt ID or a path is refused (404 with a reason) when it is absolute or holds a `..` or empty component, and an attempt ID also when it does not match `attempts`. The project file's `attempts_dir` is configuration and is opened as given, its own components included; from it, every component of the attempt ID, then of the path or the `record` name, is opened one at a time with `O_NOFOLLOW`, as is every component of the item and the `lock` path, so an attempt directory, a record, a lock file or anything in an attempt that is a symlink is never followed; so are a tab's versions and the files a tab or a column reads (section 4, "The project file"), and a version is never a symlink. A symlink in a listing is shown as a `symlink` entry with no target. Tests: [`test_files.py`](../python/tests/viz/test_files.py): `test_a_path_out_of_the_root_is_refused`, `test_a_symlink_is_listed_and_never_opened`, `test_a_symlinked_record_is_never_read`; for a tab [`test_tabs.py`](../python/tests/viz/test_tabs.py): `test_a_symlink_a_file_or_a_dot_name_is_no_version`; and for the lock file [`test_live.py`](../python/tests/viz/test_live.py): `test_a_symlinked_lock_is_never_followed`. The project file's `monitor.db` is configuration too and is opened as given, but the database, its `-wal` and its `-shm` are each refused (503 with a reason) when they are a symlink or not a regular file, checked with `lstat` just before SQLite opens them. The directory is the dataset's and its sampler's, written by the same user as the viewer runs as; a symlink put there between the check and the open is outside what the viewer guards against. Test: [`test_monitor.py`](../python/tests/viz/test_monitor.py): `test_a_symlinked_database_or_shm_is_never_opened`.
3. Content from an attempt is untrusted. Markdown is rendered with no raw HTML (it shows as text), an image is shown as a link and never loaded on its own, and a link opens only when a person clicks it, in a new tab with `noopener noreferrer`; a trace, a file and a summary are shown as text. Files are served as `application/octet-stream` with `X-Content-Type-Options: nosniff`, so a browser never runs one as a page, and every response carries a Content-Security-Policy that allows scripts, images and connections only from the viewer's own origin (images also as `data:`). Tests: [`web/src/ui/markdown.test.tsx`](../web/src/ui/markdown.test.tsx): `raw HTML shows as text`, `an image is a link, not loaded`; for a tab's Markdown [`tabs.test.tsx`](../web/src/views/tabs/tabs.test.tsx): `keeps raw HTML in the Markdown as text`; [`test_app.py`](../python/tests/viz/test_app.py): `test_files_are_served_as_bytes_with_nosniff`, `test_every_response_has_the_csp`. A definition snapshot (section 4, "The project file") is content from an attempt too: its texts, templates, values and rubrics show as text, or as Markdown rendered as above, and nothing in them runs, a template's variables included. Test: [`definition.test.tsx`](../web/src/views/definition/definition.test.tsx): `keeps raw HTML as text and runs nothing, its variables drawn in place`.
4. The server binds only `listen.host` and `listen.port` from the site file: there is no default address, and a host that is not an IP address literal, or is an unspecified one (`0.0.0.0`, `::`), is refused before anything binds. Tests: [`test_config.py`](../python/tests/viz/test_config.py): `test_the_server_binds_only_the_configured_address`, `test_a_wildcard_or_a_name_is_refused`.
5. The frontend chooses a view only by `kind`: no module under `web/src/` holds a state, output or deliverable name, and a deliverable of a kind it does not know shows as a card with its name, kind, path and reason. Tests: [`web/src/views/registry.test.tsx`](../web/src/views/registry.test.tsx): `a view is chosen by kind only`, `an unknown kind falls back to a card`; the rest is for review.
6. A site or project file loads only when it passes every check: no unknown or repeated key, each value of its type, project IDs unique and of `[a-z0-9-]`, each tone one of section 4's, `attempts_dir` an existing directory, `attempts` a pattern of plain and `*` components only, `item.depth` at least 1 and at most the number of components of `attempts`, `not_ended` a list of words, `resumable` a non-empty list of keys of `statuses`, none in `not_ended`, `lock`, `trials.diff` and `definition` relative paths of plain components, `deliverables` a list of `{name, kind, title}` with no name twice, `monitor` a mapping of `db`, a non-empty path, alone, no project called `queue` or `monitor`, `queue` a mapping of `config`, a queue file `dataforge.queue` loads, alone, `item.pattern` a regular expression, and `actions` a non-empty list, with `item.pattern`, of `{name, label, queue, argv, cwd, memory_mib, key, when, params}`: `name` of `[a-z0-9-]` and not repeated, `queue` one of the queue file's, `argv` a non-empty list of strings whose only brace is `{item}`, never in the first, `cwd` an existing absolute directory, `memory_mib` at least 1, `key` holding `{item}` and no other brace, `when` absent, `idle` or `stopped`, the last two only with `lock`, `params` absent or a non-empty list of `{name, label, flag, min, max, default, format}`, `name` of `[a-z0-9-]`, not `item` and not repeated, `flag` `--` and `[a-z0-9-]`, not repeated and not in `argv` as itself or `<flag>=…`, `min`, `max` and `default` numbers, each a value a submit may carry (invariant 10), with `min ≤ default ≤ max`, `format` absent, `number` or `usd`, and actions only with a `queue`; `tabs` a non-empty list of `{name, title, versions}`, each with `file` and, optionally, `fields`, or with `parts` alone, a list of two or more `{name, title, file, fields}`, `fields` optional, no part's `name` twice in its tab, a tab's `name` not repeated and neither `runs` nor a kind of `deliverables`, each tab's and part's `name` of `[a-z0-9-]`, `versions` a non-empty list of names, each one plain component, each `file` and each field's `file` relative paths of plain components, each `fields` absent or a non-empty list of `{title, file, field, format}`; a column's `file` a relative path of plain components and its `tab`, only with `file`, the `name` of a tab; one that fails stops the start with the file and the key that is wrong. Tests: [`test_config.py`](../python/tests/viz/test_config.py): `test_a_project_file_that_breaks_a_rule_is_refused`, `test_an_action_that_breaks_a_rule_is_refused`, `test_an_action_runs_only_in_an_absolute_directory`, `test_an_empty_list_of_actions_is_refused`, `test_a_parameter_that_breaks_a_rule_is_refused`, `test_parameters_are_a_non_empty_list`, `test_a_site_whose_queue_does_not_fit_its_actions_is_refused`, `test_an_action_s_queue_must_be_in_the_queue_file`, `test_a_project_may_not_take_a_page_s_name`, `resumable` cases of `test_a_project_file_that_breaks_a_rule_is_refused`; [`test_tabs.py`](../python/tests/viz/test_tabs.py): `test_a_tab_that_breaks_a_rule_is_refused`.
7. The record is served as the file holds it, never reshaped: `GET .../record` returns the record file's JSON as written, and the frontend reads its types from design.md section 5, ["The record"](design.md#the-record), not from a schema of its own; how a page shows a record that lacks a key or is not of that shape is section 5's "Older records". Tests: [`test_app.py`](../python/tests/viz/test_app.py): `test_the_record_is_the_file_as_written`.
8. This file has at most 200 lines. [`design-length.test.sh`](../.github/scripts/design-length.test.sh).
9. No lock is ever taken: the backend learns whether a lock file is held only from `/proc/locks` and never calls `flock`, `fcntl.lockf` or `fcntl` on it, also not to test it, since an attempt that tries to take the lock at that moment would find it busy and fail. Tests: [`test_live.py`](../python/tests/viz/test_live.py): `test_a_held_lock_is_found`, `test_a_free_lock_is_not`, `test_the_backend_never_takes_a_lock`.
10. A write is taken only from the viewer's own page and only as the project file says. It must carry `X-Viz-Write: 1`, which a page of another origin cannot send without a CORS preflight the viewer never allows; its `Host` must be `listen.host:listen.port` (an IPv6 address in brackets; the address alone at port 80, as a browser sends it) and its `Origin` `http://` and that, each header once, so that a name pointed at the address (DNS rebinding) is refused too; and its `Sec-Fetch-Site`, when sent, `same-origin`; else 403. A submit takes the action's name in its path and the item's ID as its query parameter `item`, besides it only one query parameter per parameter the action declares, named as it, and a cancel the job's ID in its path, with no other parameter, no parameter twice and no body (400). The action must be one of the project file's (404); the ID at most 200 characters, `item.depth` plain components none of which starts with `.` or `-`, matching `item.pattern` as a whole (400), of an item that has an attempt (404). A parameter's value is a plain decimal number, `-?[0-9]+(\.[0-9]{1,6})?`, of at most 15 characters, which a double holds and writes as is, from `min` to `max`, compared exactly (400); one left out takes `default`. The command is `argv` with each `{item}` replaced by the ID, then `<flag>=<value>` for each parameter in order, the value without leading or trailing zeros, a list run with no shell; a job the queue refuses is 503 without the queue's text, which may name `cwd`. Tests: [`test_actions.py`](../python/tests/viz/test_actions.py): `test_a_write_from_anywhere_but_the_viewer_s_page_is_refused`, `test_at_http_s_own_port_a_write_names_no_port`, `test_a_write_s_preflight_is_never_allowed`, `test_a_write_takes_nothing_but_the_item`, `test_a_write_takes_no_body`, `test_an_item_that_is_not_one_of_the_project_s_is_refused`, `test_an_item_that_reads_as_an_option_is_refused_whatever_the_pattern`, `test_an_action_the_project_does_not_name_is_refused`, `test_a_value_that_is_not_a_decimal_within_bounds_is_refused`, `test_a_value_at_a_bound_or_padded_is_taken_plain`, `test_a_parameter_the_action_does_not_declare_is_refused`, `test_a_job_the_queue_refuses_shows_no_path`.

## 4. Interfaces

### The site file

YAML, read with PyYAML's safe loader, held by whoever runs the viewer:

```yaml
listen: {host: 192.0.2.10, port: 8800}   # invariant 4
projects: [/path/to/dataset/viz-project.yaml]
queue: {config: queue.yaml}     # optional: dataforge.queue's queue file, relative to this file
```

### The project file

YAML, safe loader, held by the dataset in its own repo; this is the whole of what a dataset gives the viewer:

```yaml
id: example            # in URLs; [a-z0-9-]
name: Example dataset  # in the sidebar's Projects menu and the breadcrumb
color: "#e5a54b"       # the project's dot in the menu
attempts_dir: /data/example/attempts
attempts: "*/*"        # directories under attempts_dir; an attempt's ID is its path relative to it
record: record.json    # the record file, relative to the attempt's directory
definition: definition.json   # optional: the attempt's definition snapshot, relative to its directory
states: {author: {title: Author}}   # optional: a state's title in the graph and the run list; else its name
statuses: {passed: {label: Passed, tone: good}, too_easy: {label: Too easy, tone: warn}}   # an attempt status or a visit outcome: its label and tone
item: {depth: 1, title: Item, pattern: "item-[0-9]+"}   # an attempt ID's first `depth` components name its data item; `title` heads the ID column; `pattern`, optional, what an item's ID must match for an action
columns:               # extra columns of the home page, after the fixed ones
  - {title: Cap, field: [budget, max_usd], format: usd}
  - {title: Kept visit, field: [kept_visit], format: number}
  - {title: Verdict, tab: notes, file: tags.json, field: [verdict, value]}   # file, optional: read in place of the record; tab, optional, with file
session: {thinking: hidden}      # hidden (default), collapsed or expanded
not_ended: [running]   # optional: status words of an attempt that has not ended
lock: .lock            # optional: the item's lock file, relative to the item's directory
deliverables: [{name: task, kind: files, title: Task}]   # optional: what an attempt delivers once it ends
trials: {diff: verifier/patch.diff}   # optional: a trial's diff, relative to its directory
monitor: {db: ../monitor/monitor.sqlite}   # optional: relative to attempts_dir
actions:               # optional: what a data item may be put in the queue for
  - {name: again, label: Run again, queue: main, argv: [run-item, "{item}"], cwd: /srv/example, memory_mib: 2048, key: "example:{item}", when: idle,
     params: [{name: budget, label: Budget, flag: --max-usd, min: 1, max: 150, default: 75, format: usd}]}   # params optional
tabs: [{name: notes, title: Notes, versions: [notes, "notes-*"], file: out/notes.md, fields: [{title: Verdict, file: tags.json, field: [verdict, value]}, {title: Spent, file: status.json, field: [cost_usd], format: usd}]}, {name: post, title: Post, versions: [post, "post-*"], parts: [{name: report, title: Report, file: out/report.md, fields: [{title: Verdict, file: out/report.json, field: [verdict]}]}, {name: prompt, title: Prompt, file: prompt.md}]}]   # optional: tabs of the attempt page, each a Markdown file, or two or more as parts, in one or more directories of an attempt; fields optional
```

In `attempts`, a `*` matches one name that does not start with `.`. A tone is `good`, `bad`, `warn` or `neutral`; a word with no entry shows as itself, `neutral`, except `raised`, the engine's own word for an exception, which shows as itself, `bad`. A column's `field` is a list of keys into the record, as a deliverable's `Value` is (design.md, "The record"), and `format` is `text` (default), `number`, `usd`, `duration` or `time`. `session.thinking` is how a session view shows thinking blocks, `collapsed` or `expanded`, or `hidden`, the default, when this project shows none; a person opens or folds the ones shown with the session's buttons (section 5, "Session view"). `trials.diff` names the file, relative to a trial's `path` in the record, that holds the diff of what the trial's agent changed; it is a relative path of plain components, checked as `lock` is, with no glob, and a dataset whose trials leave no diff leaves it out. `deliverables` lists, in order, the deliverables the dataset's declaration names, each by the `name`, `kind` and `title` of its entry in a record (design.md, "The record"), with no other key and no name twice (invariant 6). A record has none until its attempt has taken its first step, or until it ends when an older dataforge (before #195) wrote it, and the attempt page uses this list to show what is still to come (section 5). `definition` names the file a dataset writes into each attempt's directory as the attempt starts: the definition it runs with, what the dataset gives each state's agents as it stood then, so that a page shows what the attempt read rather than what the dataset holds now. It is checked as `lock` is and read through the files route, so invariants 2 and 3 hold for it, and the viewer has no route of its own for it. An attempt whose directory has no such file, as one an older dataset ran, has no snapshot, and a page shows that as not run (L40), never as an error. The file is JSON, `{version, workflow, stages}`. `version` is `{commit, dirty, prompt_version}`: the dataset repo's commit, whether its working tree had changes, and the dataset's own version string for its prompts, each null when not known. `workflow` is `{path, format, text}`, the dataset's whole workflow file and its path in the dataset's repo, or null. `stages` is `[{state, entries}]`, one per state of the dataset's graph, in the graph's order, `entries` what that state's agents are given, in order, and empty when nothing is. An entry has a `title`, a `kind` and, optionally, a `note`, one line about it. Of kind `text`, it also has `format`, `template`, `variables` and `text`: `format`, here and in `workflow`, is a file extension without its dot, such as `md`, `toml` or `yaml`, read as `web/src/ui/file-kind.ts` reads a file's (section 5, `files`), and one the table does not know is plain text; `template` is `dollar` (`${name}`, as Python's `string.Template`), `jinja` (`{{ name }}`) or null for a text that is not a template; `variables` is `[{name, source, value, per_round}]`, one per variable of the template, `source` saying in words where its value comes from, `value`, optional, the text put in its place for this attempt, as fixed when it started, and `per_round`, optional and false when absent, true for a variable whose value changes from round to round, whose `value`, should it have one, the viewer does not show. Of kind `rubric`, it also has `rubric`, `{system, criteria}` as a rubric file of `dataforge.curation.rubric` holds them, each criterion `{id, question, check, pass_if, fail_if}` with the last three optional, and, optionally, `reads`, the names of the input blocks the review is given, in order. The viewer reads no other key and knows no dataset's files or states (invariant 5): a stage shows its state's title from `states`, else its name, and an entry of another `kind` shows as a card with its title and kind.

A dataset's record file may hold more than `Attempt.to_json()`: more top-level keys, which only a column's `field` reads, and its own `status` and `reason` in place of the engine's, such as a status word while the attempt runs. An attempt has not ended when its record's `status` is one of `not_ended`; without `not_ended`, when its `status` is null and its last visit's `outcome` is not `raised`, as the engine leaves it: `Attempt.status` is None until the attempt ends ([`engine.py`](../python/src/dataforge/curation/engine.py), `Attempt`), and an attempt a state's exception ended keeps status null after recording that visit as `raised` (design.md, invariant 12). The backend applies this rule for the listing's `live` and the `/live` route's, and the frontend, from `/api/projects`, for what it reads from the record alone, such as the attempt page's status and a run's end, where an attempt that has not ended shows as `Not ended`, never as its status word. With `not_ended`, an attempt whose `status` is null has ended with no status word, and shows everywhere as `No status`, `neutral`, a viewer word defined with the others (L37). A visit with no `outcome` shows as `Not ended` while its attempt has not ended, and once it has, as `No outcome`, `neutral`, another viewer word, wherever a visit's outcome label appears (the home page's rounds, the Runs column, a run page, the `trials` view's heading, a state's tone in the Summary's machine). `lock` names a file that a running attempt of the item holds a lock on (`flock` or a POSIX lock); it is a relative path of plain components, opened from the item's directory (`attempts_dir` and the ID's first `item.depth` components) one component at a time with `O_NOFOLLOW`, as invariant 2 opens an attempt, so it never holds `..`. The backend `stat`s it without following a symlink and looks for its device and inode in `/proc/locks` (invariant 9). Since one lock covers the whole item, an attempt that has not ended is `running` only when the lock is held and it is its item's newest attempt by `modified`; every other one that has not ended is `may have stopped`, the two cases a record alone cannot tell apart. Newest here is by `modified`, the record file's mtime and the listing's order, not by `started_at` as on the home page: a running attempt rewrites its record after each visit, while `started_at` is null until its first action has ended. An attempt whose record cannot be read has no `live` and is not its item's newest. A lock file that is missing or not a regular file counts as not held. `resumable: [canceled]`, optional, names statuses of an attempt that has ended, such as one a person canceled: such an attempt has `live` null and shows its status, never `May have stopped`, yet an action with `when: stopped` may go on with it (`when: stopped`, below). `running`, `may have stopped` and `not ended` are the viewer's own status words, defined with the others the frontend shows (L37): `running` and `not ended` `neutral`, `may have stopped` `warn`.

An action is a command for one data item, `argv` with each `{item}` replaced by the item's ID, then `<flag>=<value>` for each of its `params`, numbers a person sets on its page, each from `min` to `max` and `default` when not set, shown as a cost when its `format` is `usd`, that its page puts in the site's job queue (invariant 10), with its `queue`, `cwd`, `memory_mib` and its job's `key`, `key` with the ID too, and the labels `project`, `action` and `item`. The backend says whether it may be submitted now, for the page and again for the submit, which answers 409 with the reason: never while a job of its key is queued or running, in any queue and however it was queued; with `when: idle`, also not while the item's lock is held; with `when: stopped`, only while the item's lock is not held and the item's newest attempt by `modified` has not ended, the listing's `may have stopped`, as for going on with a killed attempt, or has ended with a status in `resumable`. The queue's own unique key keeps two submits at once to one job ([`test_actions.py`](../python/tests/viz/test_actions.py): `test_an_item_with_a_job_of_its_key_queues_no_other`, `test_a_job_another_way_queued_also_holds_the_key`, `test_idle_waits_for_the_item_s_lock`, `test_stopped_needs_a_newest_attempt_that_may_have_stopped`, `test_stopped_goes_on_with_a_resumable_status_unless_the_lock_is_held`). The conditions are read when the job is queued, not when it starts. An item that has no attempt has no page, and the viewer refuses it.

A tab shows Markdown files of an attempt that its record does not list, such as notes a dataset writes about an attempt after it ends. Its `name` is its key in `&tab=`; each of its `versions` is one name in the attempt's directory, in which `*` matches any run of characters, and a name that starts with `.` only when the pattern does. The directories they match, never a symlink or anything but a directory, are the tab's versions: in the order of the patterns, those of one pattern by name, last first, a run of digits compared as a number (`run-10` before `run-9`), a name an earlier pattern matched not again; nothing else, such as a time, orders them, and the first is the one shown by default. `file` is the Markdown, and each field's `file` a JSON file, relative to the version's directory, with `field` the keys into it. A tab of `parts` shows, in place of its one `file` and `fields`, two or more Markdown files of each version, such as the prompt an agent was given beside the report it wrote: each part has its own `name`, its key in `&part=`, `title`, `file` and `fields`, all of them read from the version shown; a tab with `file` is a tab of one part, named and titled as the tab, and the API gives both as `parts`. A column with `file` reads `field` from that JSON file in place of the record, relative to the attempt's directory, or with `tab` to that tab's first version, whatever its parts, so a column names no part. A value read from a file is `found`, JSON null among them; `not run` when the file or a directory on its way is not there, or the column's tab has no version; and `missing` when the file is there but refused (invariant 2), not JSON (`NaN` and `Infinity` included) or without the keys. Tests: [`test_tabs.py`](../python/tests/viz/test_tabs.py): `test_versions_come_in_the_patterns_order_last_name_first`, `test_a_version_with_no_markdown_yet_is_listed`, `test_fields_are_read_from_the_version_shown`, `test_each_part_of_a_tab_reads_its_own_fields`, `test_a_column_reads_its_file_from_the_tab_s_first_version`, `test_a_column_reads_its_file_from_a_tab_of_parts_first_version`, `test_a_column_s_null_is_not_its_file_not_there`, `test_a_column_with_no_file_or_version_is_not_run`.

`monitor.db` names a resource monitor's SQLite database, the source of the Monitor page. A relative path is taken from `attempts_dir`, not from the project file's directory: a deployment may copy the project file elsewhere to pin it, and the database lives beside the data, so a copy for another machine changes `attempts_dir` alone ([`test_config.py`](../python/tests/viz/test_config.py): `test_the_monitor_database_is_relative_to_attempts_dir`, `test_the_monitor_database_does_not_follow_the_project_file`). It is not checked at start, since the sampler may not have written it yet. Until it exists, every monitor route answers 404 with `{error: "no database", reason, db}`, `db` being `monitor.db` as the file writes it, or its file name alone when that is absolute, so that no page shows where the server keeps it ([`test_monitor.py`](../python/tests/viz/test_monitor.py): `test_a_missing_database_is_a_state_of_its_own`; [`test_config.py`](../python/tests/viz/test_config.py): `test_an_absolute_monitor_database_is_shown_by_its_name_alone`). The viewer reads it with five queries: (a) the runs (`runs`: `run_id`, `started_at`, `ended_at`, `stop_reason`, `source`, `pid`, `host`, `interval_s`); then, each of one run (`:run_id`) and a window `:t0` to `:t1` in seconds since the epoch, cut into 300 buckets, (b) the machine's mean and peak CPU in cores, memory used, swap and load (`machine`); (c) each container's bar, from its `container_start` event to its `container_end`, or to its last `container` row when it has none (`open`), with its `item`, `attempt` (the viewer's attempt ID), `state`, `visit`, `trial`, `image` and `exit_code`; (d) one attempt's or one container's CPU and memory, its rows summed per sample (`container`); (e) the batch's attempts, sessions, memory pool and waits (`batch`), and its pauses, from `pause_start` to the next `pause_end` or its `until` (`events`). Besides them, a window reads its run's own row (`started_at`, `ended_at`, `cpus`, `mem_total_bytes`) and, while `ended_at` is null, the `t` of its last `machine` row. A dataset whose sampler writes these tables and columns, every row with `run_id`, `sample` and `t`, gets the page. The format's version (`runs.version`) is not checked: a database that lacks a table or a column these reads name makes SQLite refuse the statement, and every monitor route then answers 503 with SQLite's reason. A value the sampler could not read is NULL in its row and draws as a gap in its curve.

### The API

Every route answers `GET` and `HEAD`, but the two writes, `POST` alone (invariant 10), and returns JSON unless it says otherwise; an error is `{error, reason}` with 400, 403, 404, 409 or 413, or 503 when a monitor database or the queue cannot be read, or the queue refuses a job; a monitor route answers a database that does not exist with `db` besides (section 4, "The project file"). An attempt is named by `?attempt=<id>`, its ID from the listing.

A sticky header with the totals (duration, cost, turns, tokens, model); a narrow gutter with the time since the start; a tool call as one line that opens to its input and output, opened from the start when it failed; more than 4 tool calls of one message folded into one line; subagent calls indented under their parent; thinking shown as `session.thinking` says, one line each when `collapsed`, none when `hidden`, and a thinking block with no text not drawn at all, not even as a row; `Expand all` and `Collapse all` in the header open or close every fold, the tool calls, the thinking and the lines before the session alike (a person's click on one fold still works after), and `startOpen` makes every fold start open, with Collapse all in view; there is no show or hide thinking button; the result badge taken from the trial's reward, not from the agent's own last word. A trace with no thinking renders as usual. The lines before the first JSON object that are not one, such as a notice the command printed before the session began, fold into one grey line at the top, their first line and how many more, which opens to show them as text (invariant 3); a line that is not JSON after the first object, and every line of a trace with no JSON object, shows where it stood, as a block of its own. Tests: [`Session.test.tsx`](../web/src/session/Session.test.tsx): `opens every fold with Expand all and closes every one with Collapse all`, `opens a thinking block with text on Expand all and closes it on Collapse all`, `starts with every fold open when told to`, `reaches the folded lines before the session with Expand all and Collapse all`, `draws a thinking block with no text as nothing, not even a row`, `shows no thinking when the project says hidden, and has no toggle`, `has no show or hide thinking button when thinking shows`.

## 6. Phases and where each part lives

Each phase owns the directories named for it and touches no other's, so P-home, P2, P3 and P4 run at once, P1 having merged. P1 wrote a placeholder in each later phase's entry module, `index.tsx` in its directory (for a view, its default export takes the deliverable or the visit and the record, for P-home the project; for P3, `web/src/session/index.tsx` exports `SessionView`), showing the deliverable's or visit's name, path and reason (on the home page, the attempt IDs), which that phase replaces. All of them develop and take screenshots against synthetic attempts in `web/fixtures/` and `python/tests/viz/fixtures/`, made by P1 (merged), which each phase may add to under a directory of its own name.

| Phase | Builds | Owns |
| -- | -- | -- |
| P1 | the backend, section 4 but for what P5 adds, and invariants 1, 2, 4, 6, 7; the shell, routes, API client and record types; shared UI (Markdown, code view and highlighting, status labels, the formatters L43 asks for, theme); the kind registry; Runs with its Summary | `python/src/dataforge/viz/`, `python/tests/viz/`, `web/` outside the directories below, `web/src/views/runs/summary/` |
| P2 | the `files` and `report` views | `web/src/views/files/`, `web/src/views/report/` |
| P3 | the session view and the `trials` view | `web/src/session/`, `web/src/views/trials/` |
| P4 | the run page | `web/src/views/runs/run/` |
| P-home | the home page, adding TanStack Table to the dependencies | `web/src/views/home/` |
| P5 | reading a dataset's real attempts: `not_ended`, `lock`, the listing's `live` and invariant 9 | `python/src/dataforge/viz/`, `python/tests/viz/` (after P1) |
| P-monitor | the Monitor page and its routes, adding uPlot to the dependencies | `web/src/views/monitor/`, `python/src/dataforge/viz/monitor.py`, `web/fixtures/monitor/` |

P1's backend modules: `config.py` (site and project files, their checks), `paths.py` (opening an attempt and a path in it, invariant 2), `app.py` (the FastAPI app and its routes) and `serve.py` (the `dataforge viz serve` command). The frontend: `web/src/api/` (the client and the record's TypeScript types), `web/src/shell/`, `web/src/ui/`, `web/src/views/registry.tsx` (kind to view). P4 renders an agent's session with P3's `SessionView` from `web/src/session/`; until P3 merges, the placeholder shows the trace's path. A change one phase needs in another's directory goes to that phase's owner, or after its merge, in a PR of its own. P-monitor, after every other phase has merged, also changes in its one PR the shared parts it needs: `config.py` (`monitor`), `app.py` (its routes), `paths.py` (503), `web/src/App.tsx` (loading the page lazily), `web/src/api/types.ts` (`monitor`), `web/src/ui/theme.css` and `theme.test.ts` (its tokens), `web/src/ui/format.ts` (bytes, cores, clock times) and the tests of each. P1 created `web/package.json` and `web/package-lock.json`; a later phase's PR that needs a new library may change them, but only one open PR changes them at a time, and once that one merges, the next merges main into its branch and regenerates the lock file.

The checks, besides the repo's Python checks with the `viz` extra installed: in `web/`, `npm ci`, then `npm run lint` (ESLint, Prettier and knip), `npm run typecheck`, `npm test` (Vitest) and `npm run build`. The backend's dependencies, FastAPI and uvicorn, are the package's optional extra `viz`, so a dataset repo that only runs attempts does not install them.
