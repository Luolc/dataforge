# dataforge viz design

The design of viz, the attempt viewer, kept apart from [`design.md`](design.md) for length; it follows the same conventions. **Planned, not built**: every part below is to be built in the phases of section 6, and once a part is built, a design PR moves it from section 6's list to the present tense, as for `design.md`; the PR that builds it describes its effect under "Design impact".

## 1. What this is, and what it is not

viz is a web viewer for the attempts a dataset runs on `dataforge.curation` (design.md section 5, ["The state machine"](design.md#5-the-state-machine)), and for the job queue of `dataforge.queue`. It shows, for each attempt, its record, the runs it made and the deliverables its declaration names, so that a person can see what a machine did and what it produced; it shows the queue's jobs, and puts a data item's actions in the queue and cancels a job, the only things it writes (invariant 1). It has two parts in this repo: a backend, the module `dataforge.viz` in the Python package, that reads attempt directories and their records and serves a JSON API and the frontend's files; a frontend in `web/`, a single-page app built with Vite, React, TypeScript, Tailwind and Radix, with every third-party library bundled, so it works with no network.

A dataset repo gives only configuration (section 4, "The project file"): where its attempts are, what its states and statuses are called and how they are coloured, how its attempts group into data items, the extra columns of its home page, its own tabs of Markdown files on the attempt page, and the actions a data item may be put in the queue for; and the pages under its entry in the sidebar, such as a snapshot page that shows the counts a file the dataset writes holds. The viewer knows no dataset: it picks a view only by a deliverable's `kind`.

Not in scope: Writing anything but the job queue: no comments, no tickets. The viewer never writes to an attempt directory (invariant 1). Running, resuming or stopping an attempt itself: an action puts the project file's command in the queue, whose scheduler runs it, and a cancel asks the queue to stop a job. A page shows what was on disk when it was read, and reads again by the browser's own reload or its refresh button; only while an attempt runs do its page and its project's home page read it again on their own, and its times go on, counted in the browser from the start its record gives (section 5, "Home page", "While it runs" and "Reading again"). Sampling a machine: the Monitor page (section 5) only reads a database a dataset's own sampler writes. Deploying: the service unit, the machine, the network and its access rules belong to whoever runs the viewer; anyone who can reach the address can also queue the project files' actions and cancel the queue's jobs. A write is taken only from a page opened at `http://<listen.host>:<listen.port>` itself, the port left out at 80 (invariant 10), so a page opened at a name for that address, or through a tunnel or a proxy at another address, can read but not write. How the built frontend reaches a machine is an open question (section 7). Showing data to people outside: the read-only share site, a process of its own ([`design-share.md`](design-share.md)).

## 2. Parts and how they connect

```text
  browser: web/ (React SPA) --- GET /api/... (JSON, files as bytes) ---> dataforge.viz (FastAPI)
                               POST /api/... (two writes, invariant 10)         |
                               GET /<anything else> (the built web/dist)        |
                                                                                 v
     site file (listen, projects, queue) -> queue file -> dataforge.queue (its SQLite database)
                                         -> project files (one per dataset) -> attempt directories
                                                                         record file (Attempt.to_json())
                                                                         artifacts/, summaries/, trials
                                                      -> monitor.db (optional, SQLite, read-only); snapshot files and their roots (optional)
```

`dataforge viz serve --config <site file> --static <dir>` starts one process. It reads the site file and each project file once at start and refuses to start when one fails its check (invariant 6); it then reads attempt directories, and a project's monitor database, and a snapshot page's file and roots, on each request, with no cache. `<dir>` is the output of `npm run build` in `web/`. The frontend talks to the backend only through the API in section 4 and draws everything from the record as written.

## 3. Invariants

Each invariant links to the tests that guard it, in `python/tests/viz/` or next to the frontend module in `web/src/`; invariant 5 is also kept by review.

1. Read-only but for the queue: no route writes, creates, moves or deletes anything, under an attempt's root or elsewhere, and every route answers only `GET` and `HEAD`, any other method getting 405, but for the two writes of section 4, "The API", which answer only `POST` and write only to the job queue, through `dataforge.queue`: a submit adds one queued job, a cancel ends a queued job or asks a running one to end, and sends its process group SIGTERM; neither writes anything else, nor takes a command, a queue or a path from the request, nor an argument but the item's ID and a bounded number for each parameter the action declares (invariant 10). Tests: [`test_actions.py`](../python/tests/viz/test_actions.py): `test_an_action_queues_its_command_with_the_item_alone`, `test_an_action_s_parameters_go_into_its_command_as_flags`, `test_a_queued_job_is_canceled_by_its_id_alone`, `test_the_queue_s_reads_write_nothing`. One more exception: the monitor routes open `monitor.db`, and the queue's, the actions', the tabs' and the listing's GETs the queue's database, with SQLite's read-only URI (`file:<path>?mode=ro`), and SQLite, opening a WAL database so, creates the database's `-wal` and `-shm` files beside it when they are missing and writes to `-shm`, as every reader of a WAL database does; nothing else in that directory or elsewhere changes, and the directory must be writable for the reader. Tests: [`test_app.py`](../python/tests/viz/test_app.py): `test_every_route_is_a_get_and_writes_nothing`; for the monitor [`test_monitor.py`](../python/tests/viz/test_monitor.py): `test_the_monitor_routes_write_only_sqlite_s_own_files`, `test_the_database_is_opened_read_only`; for the queue `test_the_queue_s_reads_write_nothing` above. With `runs`, the listing's, `/live`'s and the actions' GETs and a submit open the project's store of attempts the same way, read-only, and write nothing to it. Test: [`test_runs.py`](../python/tests/viz/test_runs.py): `test_the_store_is_opened_read_only_and_never_written`. A snapshot page's two routes (section 4, "The API") are GETs too and write nothing, to its file, its roots or elsewhere: `test_every_route_is_a_get_and_writes_nothing` above reads both.

## 4. Interfaces

### The site file

YAML, read with PyYAML's safe loader, held by whoever runs the viewer:
```yaml
listen: {host: 192.0.2.10, port: 8800}   # invariant 4
projects: [/path/to/dataset/viz-project.yaml]
queue: {config: queue.yaml}     # optional: dataforge.queue's queue file, relative to this file
```

### The project file

YAML, safe loader, held by the dataset in its own repo; this is the whole of what a dataset gives the viewer:
```yaml
id: example            # in URLs; [a-z0-9-]
name: Example dataset  # in the sidebar's Projects menu and the breadcrumb
color: "#e5a54b"       # the project's dot in the menu
attempts_dir: /data/example/attempts
attempts: "*/*"        # directories under attempts_dir; an attempt's ID is its path relative to it
record: record.json    # the record file, relative to the attempt's directory
definition: definition.json   # optional: the attempt's definition snapshot, relative to its directory
task: {deliverable: task, file: task.toml}   # optional: the attempt's Harbor task, in a deliverable of kind files, or a path relative to its directory
states: {author: {title: Author}}   # optional: a state's title in the graph and the run list; else its name
statuses: {passed: {label: Passed, tone: good}, too_easy: {label: Too easy, tone: warn}}   # an attempt status or a visit outcome: its label and tone
item: {depth: 1, title: Item, pattern: "item-[0-9]+"}   # an attempt ID's first `depth` components name its data item; `title` heads the ID column; `pattern`, optional, what an item's ID must match for an action
columns: [{title: Cap, field: [budget, max_usd], format: usd}, {title: Kept visit, field: [kept_visit], format: number}, {title: Verdict, tab: notes, file: tags.json, field: [verdict, value], labels: {needs_review: Needs review}, description: The verdict of the attempt's notes}]   # extra columns of the home page, after the fixed ones; file, optional: read in place of the record; tab, optional, with file; labels, optional, for format text: the words a page shows for each value; description, optional: what the column holds; hints, optional, for format text: a sentence for each value, shown on its cell; none, optional: a sentence shown under `—` on a cell with no value; cases, in place of field, for format text with no file: [{value, when: [{field, equals} or {field, given}]}]; filter, optional, for format text: chips that filter the items by the column
session: {thinking: hidden}      # hidden (default), collapsed or expanded
not_ended: [running]   # optional: status words of an attempt that has not ended
lock: .lock            # optional: the item's lock file, relative to the item's directory
runs: {db: ../runs.sqlite, stopped_by: {person: canceled}}   # optional: the attempts' store, relative to attempts_dir, and a status word per way an attempt was stopped; in place of not_ended and lock
deliverables: [{name: task, kind: files, title: Task}, {name: regrade, kind: trials, title: Regrade, no_trace: "No agent runs in a regrade."}, {name: pass_at_k, kind: trials, title: Pass@k, default: true}]   # optional: what an attempt delivers once it ends; default, optional, true for the deliverable of its kind that names its tab while none of the kind is reached, or {field, equals} for one that leads its kind when the data of the visit it came from has equals at field
kinds: {trials: {title: Trials}}   # optional: the title of a deliverable kind's tab
trials: {diff: verifier/patch.diff, tests: verifier/ctrf.json, kinds: {vulnerability: {label: Vulnerability}}}   # optional: a trial's diff and test results, relative to its directory; kinds, optional, a test kind's label
monitor: {db: ../monitor/monitor.sqlite}   # optional: relative to attempts_dir
actions:               # optional: what a data item may be put in the queue for

Tests: [`test_tabs.py`](../python/tests/viz/test_tabs.py): `test_versions_come_in_the_patterns_order_last_name_first`, `test_a_version_with_no_markdown_yet_is_listed`, `test_fields_are_read_from_the_version_shown`, `test_each_part_of_a_tab_reads_its_own_fields`, `test_a_column_reads_its_file_from_the_tab_s_first_version`, `test_a_column_reads_its_file_from_a_tab_of_parts_first_version`, `test_a_column_s_null_is_not_its_file_not_there`, `test_a_column_with_no_file_or_version_is_not_run`. `monitor.db` names a resource monitor's SQLite database, the source of the Monitor page. The viewer reads it with five queries: (a) the runs (`runs`: `run_id`, `started_at`, `ended_at`, `stop_reason`, `source`, `pid`, `host`, `interval_s`, and `last_t`, the `t` of its last `machine` row, null with none; [`test_monitor.py`](../python/tests/viz/test_monitor.py): `test_each_run_gives_the_time_of_its_last_machine_sample`); then, each of one run (`:run_id`) and a window `:t0` to `:t1` in seconds since the epoch, cut into 300 buckets, (b) the machine's mean and peak CPU in cores, memory used, swap and load (`machine`); (c) each container's bar, from its `container_start` event to its `container_end`, or to its last `container` row when it has none (`open`), with its `item`, `attempt` (the viewer's attempt ID), `state`, `visit`, `trial`, `image` and `exit_code`; (d) one attempt's or one container's CPU and memory, its rows summed per sample (`container`); (e) the batch's attempts, sessions, memory pool and waits (`batch`), and its pauses, from `pause_start` to the next `pause_end` or its `until` (`events`). ## 6. Phases and where each part lives

Each phase owns the directories named for it and touches no other's, so P-home, P2, P3 and P4 run at once, P1 having merged. P1 wrote a placeholder in each later phase's entry module, `index.tsx` in its directory (for a view, its default export takes the deliverable or the visit and the record, for P-home the project; for P3, `web/src/session/index.tsx` exports `SessionView`), showing the deliverable's or visit's name, path and reason (on the home page, the attempt IDs), which that phase replaces.
